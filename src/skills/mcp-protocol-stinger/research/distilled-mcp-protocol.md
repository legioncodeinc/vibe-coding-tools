## Tool vs resource vs prompt design

MCP defines three server primitives [external/mcp-spec-architecture.md]:

- **Tools** - executable functions the model invokes to perform actions (file operations, API calls, database queries, computations). Model-controlled: the model decides when to call one, based on its `name`, `title`, `description`, and `inputSchema` [external/mcp-spec-tools-primitive.md].
- **Resources** - addressable, enumerable data sources pulled by the client without model-supplied arguments (`resources/list`, `resources/read`).
- **Prompts** - reusable, parameterized message templates a user selects (`prompts/list`, `prompts/get`).

Rule of thumb, restated generally: if the model must decide arguments and trigger a side effect or a query, it is a tool. If the client should be able to enumerate and pull addressable content directly, it is a resource. If it is a canned, user-picked interaction, it is a prompt. Picking the wrong primitive is the MCP analog of putting a verb in a REST URL.

Spec-level `Tool` shape (this is the general, non-Hivemind version of "anatomy of a tool"): `name` (unique, namespaced), `title` (optional display name), `description` (routing signal for the model - it is the *only* thing the model reads to decide when to call the tool), `inputSchema` (JSON Schema), `outputSchema` (optional JSON Schema for structured results), `annotations` (behavior hints clients **MUST** treat as untrusted unless the server is trusted) [external/mcp-spec-tools-primitive.md].

Tool results carry `content` (an array of typed blocks: `text`, `image`, `audio`, `resource_link`, embedded `resource`) and, optionally, `structuredContent` (a JSON object matching `outputSchema`, which the spec requires the server to conform to and recommends the client validate against). For backwards compatibility, a tool returning `structuredContent` **SHOULD** also serialize the same JSON into a `text` block [external/mcp-spec-tools-primitive.md]. `outputSchema`/`structuredContent` is new spec surface worth knowing even if a given server (Hivemind included) only ever ships plain `text` content.

Servers that support tools **MUST** declare the `tools` capability (`listChanged` says whether the tool set can change at runtime and trigger a notification) [external/mcp-spec-tools-primitive.md]. Trust-and-safety guidance from the spec: there **SHOULD** always be a human in the loop able to deny an invocation; applications **SHOULD** show which tools are exposed, indicate when they're invoked, and confirm sensitive operations before running them [external/mcp-spec-tools-primitive.md].

## Zod input schema validation, including the v3/v4 trap

Tool `inputSchema` is typically authored with zod and converted to JSON Schema by the SDK. Field-authoring discipline, general form: every field gets `.describe(...)` (the model reads this as documentation); encode bounds (`min`/`max`, `.int()`, enums) in the type so the SDK rejects out-of-range input before your handler runs; use `.optional()` for optional params and apply the default in the handler, not the schema; register a raw shape object as `inputSchema` (`{ field: z.string(), ... }`), not a pre-wrapped `z.object(...)` - the SDK wraps it itself, and passing an already-wrapped object is a common breakage [2026-06-16-zod-v3-mcp-pin.md, 2026-06-16-mcp-sdk-typescript.md].

**The v3/v4 trap is an ecosystem-wide, versioned `@modelcontextprotocol/sdk` compatibility class, not a one-server house rule** - this is genuinely new grounding beyond the original Hivemind-only research:

- The SDK historically called zod's *internal* API (`_def`, `_parse`) rather than its public surface. Zod v4 restructured those internals, so `@modelcontextprotocol/sdk` versions built against zod v3 internals broke at *runtime* against zod v4 with errors like `w._parse is not a function` - a symptom that only appears when a tool is actually invoked, not at install or compile time [external/zod-v4-sdk-breaking-changes-issue-925.md]. This affected "all MCP servers using modern Zod versions" per the tracking issue, closed roughly 2.5 months after being filed once the SDK shipped v4 compatibility (1.23.0-beta.0) [external/zod-v4-sdk-breaking-changes-issue-925.md].
- The trap **recurs at finer version granularity even after that fix.** SDK `1.29.0` with zod `4.4.x` produces a *compile-time* type error (`ZodString` not assignable to `AnySchema`) even though the code works fine at runtime - caused by a module-identity problem where a package manager installs two separate zod copies (one nested inside the SDK's own `node_modules`, one at the top level) that TypeScript refuses to unify [external/zod-v4-4-registertool-issue-1987.md].
- **The durable rule for any new MCP server, not just Hivemind:** verify zod compatibility for your *exact* installed `@modelcontextprotocol/sdk` version before shipping, don't copy a hardcoded "always import `zod/v3`" rule from an older codebase without checking whether your SDK version already supports v4 properly. Symptoms to watch for: a runtime `_parse is not a function` (old-SDK-vs-new-zod), a compile-time `AnySchema` mismatch (version-skew within v4), or an empty/wrong generated JSON Schema on `tools/list` (zod-to-JSON-Schema conversion picking the wrong parser branch for the installed zod major version). If your dependency tree can end up with two zod instances (common with pnpm/bun), force deduplication (`overrides`/`resolutions`) rather than hoping the peer-dependency range resolves cleanly.
- Hivemind's own pin (`import * as z from "zod/v3"` at the SDK boundary, deliberately, despite `package.json` depending on zod ^4) is the *worked example* of applying this rule at one specific point in the SDK's compatibility history - see `guides/09-hivemind-worked-example.md`. Treat it as "this is what the check produced for this server at this SDK version," not as a universal constant.

## stdio vs HTTP transport selection

MCP is transport-agnostic JSON-RPC 2.0, with the transport layer explicitly responsible for connection establishment, message framing, *and authorization* [external/mcp-spec-architecture.md]. Two transports are standardized:

| Transport | Shape | Use when |
|---|---|---|
| **stdio** | Server is a child process; JSON-RPC over stdin/stdout, one client per process, stderr for logs only | Local, single-client tools; the client spawns and owns the process; per-user local credentials read from the environment |
| **Streamable HTTP** (+ optional SSE for server-to-client streaming) | Long-lived HTTP endpoint; client POSTs JSON-RPC; server can stream over SSE | Remote/multi-tenant/shared servers; the server must outlive any single client; standard HTTP auth (bearer tokens, API keys, custom headers) applies |

[external/mcp-spec-architecture.md]

Local (stdio) servers "typically serve a single MCP client," while remote (Streamable HTTP) servers "typically serve many MCP clients" concurrently [external/mcp-spec-architecture.md] - this is the spec-level version of "who owns the process, and how many clients share it," the deciding question for any transport choice.

**stdio hygiene** (general, not Hivemind-specific): nothing may write to stdout except the transport itself - stdout carries the JSON-RPC frame stream, and a stray `console.log` corrupts every message after it. All logs and fatal output go to stderr, ideally structured (one JSON object per line with `level`, `tool`, `requestId`, `durationMs`) so operators can query them [external/mcp-testing-debugging-veprompts.md]. Process managers and container setups frequently merge stdout+stderr by default, silently breaking this - verify the actual deployment, not just local `node server.js` behavior [external/mcp-testing-debugging-veprompts.md]. The uncaught/fatal path should exit non-zero and log to stderr so the client sees the process die rather than hang on a dead pipe [2026-06-16-mcp-spec-lifecycle.md].

A common, MCP-specific debugging trap distinct from stdio hygiene: GUI clients (Claude Desktop, Cursor, etc.) frequently do **not** inherit shell environment variables (`PATH`, API keys) the way a terminal session does. A server that "works when I run it by hand" and silently fails or can't find credentials when the client launches it is very often this environment mismatch, not a code defect - fix by launching the client from a terminal with the vars set, or by moving configuration into a file the client reads directly [external/mcp-testing-debugging-veprompts.md].

## JSON-RPC framing and error semantics

MCP's data layer is JSON-RPC 2.0: requests, responses, and notifications (fire-and-forget, no response expected) [external/mcp-spec-architecture.md]. Two distinct failure channels exist, and conflating them is the single most common MCP error-handling defect, restated at the spec level [external/mcp-spec-tools-primitive.md]:

1. **Protocol Errors** - a JSON-RPC `error` object (`code` + `message`), for cases where the request never reached a clean execution: unknown tool, invalid params, malformed request. Standard codes: `-32700` parse error, `-32600` invalid request, `-32601` method not found, `-32602` invalid params (the SDK raises this for you on schema-validation failure), `-32603` internal error, `-32000`..`-32099` implementation-defined server error range [2026-06-16-jsonrpc-error-model.md].
2. **Tool Execution Errors** - the tool ran; the outcome is a domain result, success or failure, reported inside a normal result with `isError: true` (API failures, invalid input data, business logic errors) [external/mcp-spec-tools-primitive.md].

The rule, stated generally: a protocol fault (bad params, unknown method) goes down channel 1; a domain outcome (empty result, not authenticated, backend down) goes down channel 2, still in-band so the model can read and react to it. Dressing a channel-1 fault as a channel-2 success (or vice versa) is the MCP analog of HTTP's "200 with an error body" [2026-06-16-jsonrpc-error-model.md]. Never leak a raw backend error string as if it were a clean result - classify it into an honest, actionable message; coerce non-`Error` rejections (`err instanceof Error ? err.message : String(err)`) so a handler never returns `[object Object]`.

## Capability negotiation

Every MCP session opens with `initialize` (client sends its protocol version + capabilities), the server's `initialize` result (protocol version it agrees to, `serverInfo` name+version, and the capability set it supports), and a `notifications/initialized` confirmation (no response expected, since it's a notification) [2026-06-16-mcp-spec-lifecycle.md]. Declared capabilities are a contract: a server that declares `resources` while registering none is lying to the client and will produce `-32601` the first time a client acts on the declaration in good faith; a server that registers tools automatically gets the `tools` capability from the SDK without hand-writing it [2026-06-16-mcp-spec-lifecycle.md].

Newer spec revisions add a stateless `_meta`-carried discovery model (`server/discover`, per-request `protocolVersion`/`clientInfo`/`clientCapabilities`, cacheable responses with `ttlMs`/`cacheScope`) [external/mcp-spec-architecture.md] - if auditing a server built against a newer SDK, check which lifecycle shape (classic `initialize` handshake vs. per-request `_meta` discovery) it actually implements rather than assuming the older shape universally applies.

Two client primitives beyond the server-side three: **elicitation** (server asks the client to gather more input from the user, current) and **sampling** / **logging** (server asks the client's LLM for a completion / pushes log notifications - both **deprecated** as of protocol version 2026-07-28; new implementations should call LLM provider APIs directly and log to stderr/OpenTelemetry instead) [external/mcp-spec-architecture.md]. Flag a server implementing sampling or logging as using a deprecated primitive, not as a defect to silently work around.

## Authentication patterns for remote/HTTP servers

Genuinely new territory for this pair - the Hivemind server never leaves stdio + a local credentials file, so the original guides had zero coverage here. The MCP Authorization spec [external/mcp-spec-authorization.md] governs this:

- **Authorization is OPTIONAL overall, but scoped by transport.** HTTP-based transports **SHOULD** conform to the spec's OAuth 2.1 flow. **STDIO transport SHOULD NOT follow this spec at all - it should retrieve credentials from the environment instead** (env vars, a local config/credentials file). This is the spec's own sanctioning of exactly Hivemind's `~/.deeplake/credentials.json` pattern: it is a deliberate, spec-correct choice for stdio, not a workaround that happens to work.
- **For HTTP servers, the spec composes existing OAuth standards rather than inventing a new one:** OAuth 2.1 (the base flow), OAuth 2.0 Protected Resource Metadata / RFC 9728 (server tells clients where its authorization server lives), OAuth 2.0 Authorization Server Metadata / RFC 8414 (client discovers the AS's endpoints), OAuth 2.0 Dynamic Client Registration / RFC 7591 (SHOULD, not MUST - clients self-register instead of needing a hardcoded client ID), Resource Indicators / RFC 8707 (binds a token to the specific MCP server it was requested for).
- **Server-side MUSTs:** implement RFC 9728 Protected Resource Metadata; return `WWW-Authenticate: resource_metadata=<url>` on `401`; validate every access token's signature *and* audience (it was issued specifically for this server, per RFC 8707) before processing any request; reject invalid/expired tokens with `401`; **never pass a client-supplied token through unmodified to an upstream API** (the "confused deputy" / token-passthrough prohibition - if the server itself calls an upstream API, it uses its own separately-obtained token there, not the client's).
- **Client-side MUSTs:** send a `resource` parameter (the canonical MCP server URI, e.g. `https://mcp.example.com/mcp`) in both the authorization and token requests; implement PKCE to protect the authorization code; send the access token as `Authorization: Bearer <token>` on every request (never in the URL query string), even within one logical session.
- **Wire-level pattern for the common "just needs an API key" case** (bearer token / API key auth, the lighter-weight alternative to full OAuth that HTTP transport supports natively): a static or rotating token sent as `Authorization: Bearer <token>` or a custom header, validated server-side per request since HTTP is stateless - "every single request needs to independently prove it's authorized" [external/mcp-testing-three-layers-autonoma.md]. This is simpler to stand up than full OAuth 2.1 + PRM discovery but does not give you token audience binding, scoped permissions, or a standard discovery flow; treat it as an acceptable minimum for a low-stakes internal HTTP server, and escalate to full OAuth 2.1 per the spec above once the server is exposed publicly or handles sensitive data.
- **Security musts regardless of flow:** HTTPS on every authorization-server endpoint; redirect URIs are `localhost` or HTTPS only, matched exactly (no open-redirect surface); short-lived access tokens; refresh-token rotation for public clients; `state`-parameter verification on the authorization-code callback.
- **Auth failure error codes:** `401` (missing/invalid token), `403` (valid token, insufficient scope), `400` (malformed authorization request) [external/mcp-spec-authorization.md].
- **Auth-specific test triad**, distinct from ordinary functional tests: rejection (no/invalid credential refused *before* any tool logic runs), scoping (two valid credentials with different permissions see different tool lists/results, not a client-side filter a slightly different request could bypass), expiry/refresh (a token that expires mid-session fails cleanly on the *next* call; a refreshed token is picked up without a full reconnect) [external/mcp-testing-three-layers-autonoma.md].

## Testing an MCP server

Three independent practitioner sources, published within weeks of each other in 2026, converge on the same layered shape - cited together as convergent consensus, not one blog's opinion [external/mcp-testing-three-layers-autonoma.md, external/mcp-server-testing-production-guide-yaw.md, external/mcp-testing-debugging-veprompts.md]:

1. **Protocol / handshake layer** - no LLM involved. Does `initialize` complete, does `tools/list` return well-formed schemas, does `tools/call` return valid JSON-RPC. Tooling: the official MCP Inspector's CLI/headless mode (`npx @modelcontextprotocol/inspector --cli`), scriptable in CI with `jq` assertions on the JSON-RPC shape [external/mcp-testing-three-layers-autonoma.md].
2. **Deterministic handler/unit layer** - the tool's underlying function, imported and called directly, with zero MCP framing in the loop. Keep handler logic in plain functions with no transport dependency so this layer stays fast and exact-match. This is where Hivemind's existing boundary-mock Vitest pattern lives (see `guides/07-testing-mcp.md` and the Hivemind worked example) - it is the general industry-standard shape, not a Hivemind invention.
3. **Integration layer** - a real (or in-memory-transport) MCP client connected to the real server, asserting protocol-level behavior with *known* argument shapes: correct tool list, correct parameter validation, correct response format. Catches schema mistakes invisible to layer 2 (e.g. a schema marks a param `required` while the handler treats it as optional - the client refuses to call the tool before the handler ever runs) [external/mcp-testing-debugging-veprompts.md].
4. **Tool-selection / end-to-end layer** - probabilistic, not deterministic. Given a natural-language prompt, does a real model pick the right tool with the right arguments, run N times (10-20 as a floor) and assert on semantic/property conditions, not exact-match, because a single run only proves the happy path is *possible* [external/mcp-testing-three-layers-autonoma.md]. **The harness pattern** is the fix for brittle E2E assertions: instead of asserting the exact tool call, assert the eventual system state (did a customer with that email end up in the fixture store), because the model can take multiple valid paths to the same correct outcome [external/mcp-server-testing-production-guide-yaw.md]. Run E2E suites on a schedule (not every push - they're slow and non-deterministic), score success rate across many runs rather than pass/fail once, and include negative prompts that should produce a graceful refusal rather than a hallucinated success [external/mcp-server-testing-production-guide-yaw.md].
5. **Transport-specific tests**, one class per transport actually shipped: stdio (process lifecycle - starts, completes handshake, exits cleanly on disconnect without leaking a zombie); HTTP (every request independently proves authorization since HTTP is stateless - test the no-header, expired-token, and under-scoped-token cases specifically); SSE (incremental frame parsing as data arrives, and reconnect/resume after a dropped connection - "the failure mode that never shows up in local development and always shows up in production behind a load balancer") [external/mcp-testing-three-layers-autonoma.md].
6. **CI checklist**, general-purpose: type-check + lint every PR; unit tests per handler; Inspector in headless mode to verify tool discovery; confirm the built artifact launches with the documented command; check no secrets are logged to stderr; validate tool output against the MCP content schema; run transport tests for whichever transports are shipped; one smoke test against a real client config before releasing [external/mcp-testing-debugging-veprompts.md].

## Registering a server in each of the four harnesses

Reused wholesale from queen-bee-stinger's already-researched four-harness digest - `mcp-protocol-stinger` does not re-research harness registration mechanics, only the protocol content that goes inside the registered server. See `guides/08-harness-registration.md` for the operational how-to; this section is the citation trail.

- **Claude Code** registers MCP servers in `.mcp.json` at the project root (or `~/.claude.json` for user/per-project scope) - a standard flat `mcpServers` map, evaluated per the Managed > CLI args > Local > Project > User precedence order like all Claude Code configuration [queen-bee-stinger/distilled-research-articles.md, lines ~21-42]. Inside a plugin, `.mcp.json` lives at the plugin root (never nested inside `.claude-plugin/`) and can use `${CLAUDE_PLUGIN_ROOT}`-style path variables [queen-bee-stinger/distilled-research-articles.md, lines ~373, ~1973].
- **Cursor** uses its own `mcp.json`, the same JSON `mcpServers`-map shape as Claude Code, which is why the two are easy to confuse with Codex's format (see the TOML trap below).
- **ChatGPT Codex uses TOML, not JSON, for MCP config - and this is a documented, named trap.** Codex's MCP config lives in `config.toml` (`~/.codex/config.toml`, or `.codex/config.toml` for trusted projects), shared across the Codex CLI, IDE extension, and desktop app. **Pasting a Claude Code/Cursor-style `mcpServers` JSON block into Codex's config silently fails - the correct root key is `mcp_servers` (underscore), not `mcp.servers` or `mcp-servers`, and the file format itself is TOML, not JSON** [queen-bee-stinger/distilled-research-articles.md, line 1495: "**TOML trap.** Codex uses TOML, not JSON, for MCP config — pasting a Claude Code/Cursor-style `mcpServers` JSON block silently fails. Correct root key is `mcp_servers` (underscore), not `mcp.servers`/`mcp-servers`."]. Stdio servers use `command`/`args`/`env`/`cwd` keys; HTTP servers use `url`/`auth` (`oauth` default or `chatgpt`)/`bearer_token_env_var`/`http_headers` keys; shared keys include `startup_timeout_sec` (default 10), `tool_timeout_sec` (default 60), `enabled`, `required`, `enabled_tools`/`disabled_tools`, and `default_tools_approval_mode` [queen-bee-stinger/distilled-research-articles.md, lines 1505-1529]. `codex mcp add <name> -- <stdio-command>` is the CLI path; there is no `enable`/`disable` subcommand as of the research date - toggle the `enabled` key by hand [queen-bee-stinger/distilled-research-articles.md, line 1503]. Codex cloud does not support MCP at all as of the research date - only the CLI, IDE extension, and desktop app read the shared local `config.toml` [queen-bee-stinger/distilled-research-articles.md, line 1531].
- **Claude Cowork's connector model requires the MCP server to be reachable over the public internet, not localhost - this is a hard architectural constraint, not a configuration nuance.** Cowork connectors "reach external services through Anthropic's cloud, not your local network - a custom connector must be reachable over the public internet from Anthropic's IP ranges" [queen-bee-stinger/distilled-research-articles.md, line 1885: "Connectors | MCP servers giving access to an external service | In Cowork, connectors reach external services through Anthropic's cloud, not your local network — a custom connector must be reachable over the public internet from Anthropic's IP ranges"]. Practically: a stdio server that only ever runs as a locally-spawned subprocess (Hivemind's own architecture) **cannot** be registered as a Cowork connector without first standing up an HTTP-reachable, publicly-addressable deployment of it - this is a transport-and-deployment decision, not just a config edit, and should be escalated rather than silently attempted. Cowork plugin packaging still bundles MCP config the same way as Claude Code (`.mcp.json` at the plugin root, shared package format - "a plugin built for one works in the other") [queen-bee-stinger/distilled-research-articles.md, line 1878], but the *reachability* requirement is Cowork-specific and does not apply to Claude Code or Cursor, which spawn the process locally.
