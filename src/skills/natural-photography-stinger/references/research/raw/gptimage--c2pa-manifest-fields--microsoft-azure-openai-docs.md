# Content Credentials in Azure OpenAI — concrete C2PA manifest fields
- URL: https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-credentials
- Fetched: 2026-08-17
- Source type: official-docs (Microsoft, for OpenAI image models hosted on Azure)

Archived because it is the only primary source found that names **actual C2PA
manifest field names and values** for OpenAI image output. OpenAI's own help
article describes the manifest only in prose.

## Manifest fields (verbatim table)

| Field name | Field content |
|---|---|
| `"description"` | `"AI Generated Image"` for all generated images, attesting to the AI-generated nature of the image. |
| `"softwareAgent"` | `"Azure OpenAI DALL-E"` or `"Azure OpenAI ImageGen"` — for images generated by DALL·E series models or GPT-image-1 series models in Azure OpenAI. |
| `"when"` | The timestamp of when the content credentials were created. |

## Signing certificate

- Cryptographically signed by a certificate that traces back to Azure OpenAI.
- Issuing organization: **Microsoft Corporation**.

## Caveats (important)

- These `softwareAgent` values are **Azure-specific**. Images generated through
  OpenAI's own API will carry an OpenAI-issued certificate and a different
  `softwareAgent` string; OpenAI does not publish the exact value.
- The doc names DALL·E series and **GPT-image-1 series** models. It does not
  yet enumerate `gpt-image-2`.
- The doc does **not** document other C2PA assertions such as
  `digitalSourceType` (the C2PA/IPTC field that would carry
  `trainedAlgorithmicMedia`) or the `c2pa.actions` list. Those may be present in
  the manifest but are not documented here.

## Verification tooling referenced

- Content Credentials Verify — contentcredentials.org/verify
- Content Authenticity Initiative open-source tools — opensource.contentauthenticity.org
- (OpenAI's own tool: openai.com/verify, which also checks SynthID)

## Practical note

Because the manifest carries a signed timestamp and an explicit
"AI Generated Image" description, a photorealistic image delivered with its
Content Credentials intact is self-disclosing. Any workflow that re-encodes to
JPEG/WebP through a tool that does not preserve XMP/JUMBF will silently drop
it — which is a documentation problem for the deliverer, not an automatic
policy violation (see the provenance-policy-stance file).
