## Hosted provider landscape: dimensions, pricing, input discipline

**OpenAI** (source: openai--vector-embeddings-guide.md) ships `text-embedding-3-small` (1536 dim default, $0.02/M tokens) and `text-embedding-3-large` (3072 dim default, $0.13/M tokens), both Matryoshka-trained (MRL): pass `dimensions: N` at request time to get a shorter vector directly, or truncate a stored vector yourself and re-normalize to unit length (L2 norm) afterward, since cosine similarity on an un-renormalized truncated vector is wrong. OpenAI recommends cosine similarity as the distance function; their embeddings are pre-normalized to length 1, so cosine and Euclidean distance rank identically and cosine reduces to a plain dot product.

**Cohere** (source: cohere--embed-api-v2-reference.md) requires `input_type` on every call to embed-v3+: `search_document` for corpus-side embeddings, `search_query` for query-side, plus `classification`, `clustering`, `image`. This is an asymmetric embedding scheme, embedding the same text as a document versus as a query produces different vectors, and using the wrong one degrades retrieval without erroring. `embed-v4` adds `output_dimension` (256/512/1024/1536, default 1536) and can return multiple `embedding_types` in one call (`float`, `int8`, `uint8`, `binary`, `ubinary`, `base64`).

**Voyage AI** (sources: voyageai--text-embeddings-model-choices.md, voyageai--flexible-dimensions-and-quantization.md, voyageai--pricing.md) runs the same asymmetric pattern via `input_type=query|document`, which prepends a fixed instructional prefix ("Represent the query for retrieving supporting documents: " / "Represent the document for retrieval: ") rather than changing model weights per call. The current voyage-4 family (`voyage-4-large`, `voyage-4`, `voyage-4-lite`, `voyage-code-4`) is Matryoshka-trained with `output_dimension` in {256, 512, 1024 default, 2048} and supports quantized `output_dtype` (`int8`/`uint8`/`binary`/`ubinary`) for 4x-32x storage reduction. Pricing is token-based with a large free tier (200M tokens for the voyage-4 family) and a 33%-discounted async Batch API with a 12-hour completion window. Voyage also publishes one open-weight model, `voyage-4-nano`, on Hugging Face, the one Voyage model runnable locally instead of via their hosted API.

**Cross-provider pattern:** all three hosted providers now train with Matryoshka Representation Learning and expose it as a request-time `dimensions`/`output_dimension` parameter, and all three offer a discounted async batch lane (see openai--vector-embeddings-guide.md for the OpenAI $ figures cited above, docs.voyageai.com/docs/pricing for Voyage's, and the general batching source below for the mechanism). Treat "does this model support Matryoshka truncation to my target width" as a cheap-vs-expensive gate before ever recommending a genuine model swap: truncation is a post-hoc slice-and-renormalize with no re-embedding call; a real model or width change outside the trained Matryoshka set is always a full re-embed (source: voyageai--flexible-dimensions-and-quantization.md).

## The local/self-hosted option: transformers.js

The existing local-daemon material (nomic-embed-text-v1.5 via `@huggingface/transformers`) is one instance of a general pattern confirmed by the official transformers.js docs (source: huggingface--transformersjs-node-server-side-inference.md): `@huggingface/transformers` runs natively in Node.js (18+) with no separate Python process, via a singleton `pipeline()` wrapped so the model loads once and is reused, structurally the same warm-process principle as this stinger's existing daemon guide. Three `env` settings matter for a genuinely offline/local-only setup: `env.cacheDir` (where downloaded model weights are cached after first run), `env.localModelPath` (point at pre-downloaded files instead of the Hub), and `env.allowRemoteModels = false` (hard-disable any network fetch of models, the mechanism that actually guarantees "nothing leaves the machine" at model-fetch time, not just at inference time). Custom or unsupported models are convertible to the ONNX format transformers.js consumes via Hugging Face's `Optimum` tool.

## Choosing a model: a general rubric, not a leaderboard tour

The Qdrant model-selection guide (source: qdrant--how-to-choose-an-embedding-model.md) generalizes the "match the model to your data, not a public benchmark" principle already applied to the Hivemind-scoped rubric in `guides/local-daemon-03-embedding-model-selection.md`: MTEB and similar leaderboards rarely represent domain-specific data, so build a small ground-truth set (a few hundred query-to-relevant-document pairs, even a few dozen to start) and measure `precision@k`/`MRR`/`NDCG` on your own corpus before trusting a public score. Tokenizer/language fit is an easy-to-miss failure mode: an embedding model can only understand tokens its tokenizer was trained on, and unsupported characters become `UNK` tokens that can make semantically opposite text look like a near-match.

Production selection is a three-way operational tradeoff, not just a quality number: **throughput** (embeddings/sec, larger models are typically slower, can bottleneck bulk ingestion), **latency** (time to one embedding, matters for interactive search-as-you-type or chat, quantization of larger models narrows this gap), and **cost** (infrastructure cost for self-hosted vs per-token cost for hosted; self-hosting trades higher upfront cost for lower marginal cost, but only past a real utilization threshold, not by sticker price alone). A model that is 1% more precise but 10x slower and 10x more resource-hungry is usually not worth it; match to the actual product surface (a batch job wants throughput, a live search box wants latency, an LLM-backed pipeline downstream of retrieval may prioritize cost since retrieval isn't the slow part).

## Batching

Embedding calls have a fundamentally different networking profile from LLM completions: no autoregressive decode, so latency is network-round-trip-dominated rather than compute-dominated, and a single call typically completes in 50-200ms versus 1-10s for a short LLM completion (source: speedtesthq--embedding-api-networking.md). Because of this, batching is close to mandatory for any bulk workload: sending 1000 documents one-at-a-time means 1000 HTTP round trips dominated by network overhead, while batching into groups of 50-500 collapses that to single or double-digit request counts dominated by actual inference time. Batch as large as the API's stated per-call limit allows for background/bulk indexing; batching does not apply to a single interactive query-time embed (there's nothing to batch). Dimension choice compounds with batch volume on bandwidth: a 1536-dim float32 vector is 6KB, so embedding 100M documents at that width moves roughly 600GB of vector data alone, before the input text itself; this is the same storage-cost argument that motivates Matryoshka truncation and quantization at scale (source: speedtesthq--embedding-api-networking.md, cross-referenced with voyageai--flexible-dimensions-and-quantization.md).

## Caching: avoiding re-embedding identical text

Embeddings are a pure function of `(model, text)`, deterministic with no sampling or context dependency, which makes them the easiest thing in an AI pipeline to cache safely, unlike an LLM-answer cache, a cache hit is behaviorally indistinguishable from a fresh call (source: devto--caching-embeddings-in-node-60-line-layer.md). Three points recur across both dedicated caching sources and are treated as load-bearing, not optional:

1. **The cache key must be `(model_name, model_version, content_hash[, dimension])`.** Leaving the model out of the key is the single most common mistake: a text-only key silently returns a vector from the wrong model after a swap, and the resulting distances are meaningless with no error raised. Leaving dimension out breaks any provider that supports variable-width output (source: devto--caching-pre-computed-embeddings-ttl-versioning-cold-start.md, devto--caching-embeddings-in-node-60-line-layer.md).
2. **Key on a content hash, not a document ID.** A document-ID key serves a stale vector after an edit; a normalized-text SHA-256 hash makes an edit a cache miss automatically, which is the correct behavior.
3. **TTL is almost never the right invalidation mechanism.** Embeddings go stale only when the source text changes or the model changes, and the key already encodes both. Use a TTL only as a memory-eviction bound on a hot cache, or for genuinely short-lived content governed by a retention policy, not as a freshness signal.

A model swap invalidates the whole cache by construction (old and new vectors are not comparable); the two practical migration paths are a stop-the-world re-embed under a maintenance window (simplest, fine under roughly a million chunks) or a dual-write-with-flag rollout that keeps reads available throughout at the cost of writing twice until cutover (source: devto--caching-pre-computed-embeddings-ttl-versioning-cold-start.md). On day zero with an empty cache, guard against a stampede with backfill-before-cutover (populate offline through a discounted batch endpoint before live traffic arrives) and a single-flight pattern on the read path (collapse concurrent misses on the same key into one in-flight API call rather than firing N duplicates for a newly-popular chunk).

At the storage layer, encode cached vectors as raw `Float32Array` bytes rather than JSON arrays of decimals, roughly half the size and no JSON parse/stringify cost, with a batch-shaped cache interface (`getMany`/`setMany`) so a batch of N texts costs one round trip to the cache store instead of N (source: devto--caching-embeddings-in-node-60-line-layer.md).

## Local vs hosted: when each wins

The Qdrant selection guide's framing (throughput/latency/cost as first-class, not an afterthought to quality) is the clearest embedding-specific version of the local-vs-hosted tradeoff archived in this pass. Self-hosting trades a higher upfront cost (install, memory, ops) for a lower marginal cost per embedding and full data locality (nothing transits a third party); hosted APIs trade per-token billing and network dependency for zero operational burden and no model/runtime maintenance. Neither is a universal default: teams with existing ops capacity and budget constraints lean self-hosted; teams that want to avoid infrastructure management lean hosted even at a per-token cost premium (source: qdrant--how-to-choose-an-embedding-model.md). This is consistent with, and generalizes, the existing local-vs-hosted framing already written for the Hivemind-specific case in `guides/local-daemon-06-local-vs-hosted.md` (privacy, zero per-call cost, offline operation as the case for local; footprint on a thin host or a measured recall gap as the case for hosted); this pass keeps that guide's Hivemind-specific reasoning intact and adds the general provider-selection layer in `guides/00-selection-matrix.md`.
