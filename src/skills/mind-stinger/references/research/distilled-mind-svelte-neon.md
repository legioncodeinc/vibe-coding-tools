# Distilled: SvelteKit streaming and Neon + pgvector for this repo's cognitive layer

Synthesis of the raw sources in `references/research/raw/` for this pass's broadening of mind-stinger: Neon Postgres plus pgvector as this repo's default retrieval substrate, and SvelteKit `+server.ts` patterns for streaming an LLM response on Vercel. The pre-existing Qdrant/Cohere/Valkey/OpenRouter research trail in `research/2026-04-25-*.md` is unchanged and remains the sourcing for the alternative stack documented from `guides/01-stack-enforcement.md` onward.

## Streaming an LLM response from a SvelteKit server endpoint

A SvelteKit `+server.ts` route handler is, per the framework's own description, "a machine for turning a `Request` into a `Response`" built directly on Web Standard APIs (source: sveltekit--kit-web-standards-stream-apis.md). The `Response` constructor accepts a `ReadableStream` as its body, which is the mechanism for both large-payload streaming and Server-Sent Events. The framework docs carry one hard caveat: this only actually streams to the client on platforms that do not buffer the whole response first, explicitly naming AWS Lambda as an example that would buffer it (source: sveltekit--kit-routing-streaming-response.md).

That caveat does not disqualify Vercel, even though Vercel's Node.js runtime is Lambda-backed. Vercel built a dedicated bridge specifically to make HTTP streaming work over Lambda: the request routes through an Edge Location to a Serverless Function Invocation Service, which injects a callback URL before forwarding to Lambda; inside Lambda a bridge opens a socket back to that callback URL and streams bytes over it as they're produced, and the Invocation Service relays them to the client incrementally (source: vercel--functions-streaming-serverless-node-edge-and-duration.md). Streaming from a `+server.ts` handler on Vercel's default Node.js runtime works because of this Vercel-specific engineering, not because Lambda gained native streaming support.

Two concrete implementation paths, both grounded in archived sources:

**Vercel AI SDK path (`ai` + `@ai-sdk/svelte`).** The documented quickstart wires `streamText()` (model provider, message array) into `toUIMessageStream()` and `createUIMessageStreamResponse()`, returning a ready-made streaming `Response` directly from the `+server.ts` handler (source: ai-sdk-dev--svelte-quickstart-streamtext.md). The SDK is provider-agnostic: swapping the default Vercel AI Gateway provider for a direct `@ai-sdk/openai` or `@ai-sdk/anthropic` instance, or any OpenAI-compatible client (which covers OpenRouter, since OpenRouter's endpoint is OpenAI-compatible), is a one-line change. Adopting `streamText()` for response shaping does not require dropping OpenRouter as this repo's LLM gateway when a project already runs the alternative stack; the two choices are independent.

**Raw `ReadableStream`/SSE path (no SDK).** The sveltejs/kit project's own long-running issue thread for streaming examples has the reference pattern the wider ecosystem copies: enqueue encoded chunks into a `ReadableStream` (or a `TransformStream` bridged to an event source) and return `new Response(readable, { headers: { 'content-type': 'text/event-stream' } })` (source: sveltejs-kit--issue-5344-sse-readablestream-examples.md). The same thread carries a load-bearing defensive-coding fact for anyone parsing a stream manually: chunks are not guaranteed to end at convenient boundaries. A UTF-8 sequence, an SSE frame, or a JSON token from an LLM provider's stream can be split arbitrarily across `read()` calls; code that assumes one read equals one complete unit will intermittently corrupt output under real network conditions. Any hand-rolled (non-SDK) streaming implementation needs a small buffering/reassembly layer for this reason, not just a naive chunk-forwarding loop.

**Runtime choice on Vercel: default to the Node.js runtime, not Edge.** Vercel's own Edge runtime docs, as of the 2026-08-03 revision, open by recommending migration away from Edge to Node.js for "improved performance and reliability," a reversal of the platform's earlier position that favored Edge specifically for streaming (source: vercel--edge-runtime-official-docs.md). Two independent reasons this matters for this repo specifically: Fluid compute erased the old cold-start/idle-cost tradeoff that used to justify Edge, and the Edge runtime's Web-Standard-API-only constraint means "a number of database drivers that assume a Node socket layer will not run there" (source: digitalmatters--vercel-edge-vs-serverless-2026.md), which is a direct problem for a Neon Postgres connection running inside the same request that streams a retrieval-augmented completion. The default recommendation for this repo's streaming LLM endpoints is therefore the standard Node.js Vercel Function runtime, with Edge reserved for genuinely latency-critical Web-Standard-API-only logic (auth checks, redirects), not full RAG request handling.

**Duration and connection-liveness limits to design against.** Current Vercel Function duration limits: Hobby 300s max, Pro/Enterprise 300s default extendable to 800s (1800s in beta on supported runtimes) (source: vercel--functions-streaming-serverless-node-edge-and-duration.md). For a long-running agentic or multi-step LLM response that could approach these windows, an explicit `maxDuration` route config is needed on paid plans, or the work should move to a background/async architecture. Separately: Vercel keeps long-held HTTP/2 streaming connections alive with idle `PING` frames, but HTTP/1.1 has no equivalent, so any HTTP/1.1 hop (a corporate proxy, an older client) can silently drop an idle connection; the documented mitigation is to emit periodic heartbeat or progress chunks while work is running rather than going silent between tokens.

## Neon Postgres plus pgvector as this repo's default retrieval substrate

pgvector ships enabled on every Neon project; enabling it per database is one statement, `CREATE EXTENSION IF NOT EXISTS vector;` (source: neon--vector-search-guide-pgvector.md). A vector column is declared with a fixed dimensionality matching the embedding model's output width (`VECTOR(n)`), and pgvector exposes three distance operators used in `ORDER BY`: `<->` (Euclidean/L2), `<=>` (cosine, the standard choice for text embeddings), and `<#>` (negative inner product, used for maximizing similarity). An HNSW index (`CREATE INDEX ... USING hnsw (column vector_cosine_ops)`) replaces the default sequential scan for approximate nearest-neighbor search at scale.

A production-shaped write-up (source: jacar-es--pgvector-production-poc-to-slo.md, dated 2026-06-09, updated 2026-07-12, citing ANN-Benchmarks 2025 and a named Timescale April 2026 benchmark) supplies the concrete schema and tuning defaults this stinger now recommends for this repo:

- **Split `documents` from `chunks`.** The document is the business/permissions/deletion unit; the chunk is the retrieval unit. Carry `tenant_id` on both tables deliberately (not just derivable via a join), because the hot retrieval query needs it directly for filtering, for a partial index or partition, and for Row-Level Security. This maps directly onto this stinger's existing per-tenant-isolation rule, previously stated only in Qdrant payload-filter terms; the same rule now applies to pgvector's `chunks.tenant_id` column and its index.
- **HNSW build parameters:** `m = 16` (edges per graph node, higher raises recall at the cost of size/build time), `ef_construction = 64` (build-time search depth, 128-256 for a better graph at higher build cost). Runtime: `hnsw.ef_search` (session-scoped GUC, default 40) is raised per-session until the recall target is hit and no further, since every increase costs latency. The index's operator class must match the query's distance operator or Postgres silently falls back to a sequential scan instead of erroring, a gotcha worth flagging on any RAG audit of a pgvector-backed feature.
- **The filtering-at-scale "recall cliff":** pgvector's HNSW index applies a metadata filter (like `tenant_id`) *after* building its top-k candidate set, not inside the graph traversal. A highly selective filter can leave far fewer results than requested. Mitigations, in order of applicability for this repo: a partial index or partition per tenant when tenant is the dominant filter, raising `ef_search` for moderately selective filters, or pgvector 0.8's iterative scan (`hnsw.iterative_scan`) for the general case. This is the one structural weakness pgvector has relative to Qdrant (which filters inside its index traversal) and is the primary "escape hatch" signal toward the alternative stack, matching the framing `vector-store-stinger`'s own selection matrix already documents.
- **Two-stage reranking still matters on pgvector.** A wide, cheap HNSW cosine sweep for candidates, then a cross-encoder reorder to the final top-N. The production write-up states a 10-15% relevance drop from skipping this stage, measured on the author's own datasets. This is the same shape as the Cohere `rerank-v3.5` two-stage pipeline already documented for the alternative stack; on pgvector the rerank stage can be a local cross-encoder or a managed API (including Cohere Rerank, which is not exclusive to the Qdrant path).
- **Hybrid search (BM25 plus vector) fused with Reciprocal Rank Fusion** recovers exact-term matches (product codes, proper names, version numbers) that embeddings miss; in Postgres this is native `tsvector`/`tsquery` or ParadeDB's `pg_search` for a true BM25 implementation.
- **Cited production SLOs** worth adopting as this repo's retrieval targets when running pgvector: end-to-end p95 latency under 700ms for a single-turn response (up to 1500ms with rerank plus a large model in the pipeline), recall@10 at or above 0.85 (alert below 0.80), and a monitored cost-per-thousand-queries budget.

**A forward-looking, non-default fact worth recording:** Neon also ships an experimental `pgrag` extension that runs an entire RAG pipeline (text extraction, chunking, local embedding, local reranking, and even the chat completion call) directly in SQL, layered on top of pgvector (source: neon--pgrag-extension-official-docs.md). It is explicitly experimental and is not this stinger's recommended default path (the default stays: application-layer embedding call plus pgvector storage plus application-layer rerank, matching `vector-store-stinger`'s own pgvector guides), but it is evidence that in-database embedding/reranking is a real, shipping option now, worth revisiting if the team's cost or latency needs change.

## What this means for the stack-flip

The two prior framings pointed in opposite directions: the old `references/generic-vector-db-choice.md` treated pgvector as a demoted alternative "for context only," and the old `guides/00-principles.md` opened directly on the Qdrant/Cohere/Valkey/OpenRouter stack as the unconditional canonical default. For this repo specifically, the sourcing above supports flipping that: Neon already runs pgvector with no additional infrastructure, the schema and tuning patterns are mature and documented in production, and the one real structural gap relative to Qdrant (filtering at scale) is a named, well-understood tradeoff with a documented mitigation path and a clear escalation trigger, not an unknown risk. Qdrant, Cohere rerank, Valkey, and OpenRouter remain fully valid, fully documented as the alternative stack in `guides/01-stack-enforcement.md` onward, for any project that already runs that stack or has a specific need (very large corpora, heavy metadata filtering, a strict no-ops requirement) that the escalation triggers above call out.

## Open questions carried forward
