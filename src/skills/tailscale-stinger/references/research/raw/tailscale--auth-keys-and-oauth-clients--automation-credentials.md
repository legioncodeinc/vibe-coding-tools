# Auth keys and OAuth clients for automation

- URL: https://tailscale.com/kb/1085/auth-keys ; https://tailscale.com/kb/1215/oauth-clients
- Fetched: 2026-08-14
- Source type: Official docs
- Component: Auth keys / OAuth clients

## Content

### Auth keys

Pre-authentication keys let a device register **without** an interactive browser login - the natural fit for containers, IoT, or infrastructure-as-code (e.g. Terraform).

- **User identity by default**: an auth key generated by a person authenticates the new device *as that person*, unless the key carries **tags**, in which case the device takes on the tag identity instead. For any service/automation device, always generate a **tagged** key.
- **One-off** keys: single use, then Tailscale auto-revokes them. **Reusable** keys: multiple devices can register with the same key - "be very careful with reusable keys, they're best kept in a key vault."
- **Expiry**: 1 to 90 days, chosen at creation; defaults to the 90-day max if unspecified. Expiry of the *key itself* is independent of the *node key* of a device that already registered with it - a device stays authorized on its own node-key expiry schedule (default 180 days) even after the auth key that provisioned it expires.
- **Tagged-device key expiry is disabled by default** on first tag+auth (consistent with the tags raw file) and does not change on a later tag edit alone - only re-authentication flips it.
- Device-setting toggles at generation time: **Ephemeral** (auto-remove on disconnect), **Pre-approved** (skip manual device approval if that's enabled tailnet-wide), **Tags** (bake in the tag identity).
- Revoking a key does **not** deauthorize devices already registered with it - that requires deleting the device itself from the Machines page.
- Best-practice recommendations by scenario: **ephemeral** for short-lived workloads (containers, Lambda), **pre-approved** for servers on a device-approval-enabled tailnet, **pre-signed** for Tailnet-Lock tailnets, **tagged** for any shared/service device.

### OAuth clients

The mechanism for **ongoing, scoped, programmatic access to the Tailscale API** itself (not just for registering nodes) - client-credentials OAuth 2.0 flow.

- An OAuth client = **Client ID + Client secret**, scoped to specific **API scopes** (e.g. `dns:read`, `devices:core`) at creation. Tailscale restricts a scoped token to only the API endpoints that scope covers.
- **API access tokens expire after exactly 1 hour, non-configurable** - client code must refresh proactively; OAuth libraries in Go/Node/PHP/Ruby/Rust handle this.
- Token endpoint: `https://api.tailscale.com/api/v2/oauth/token` (standard OAuth 2.0 client-credentials request/response shape).
- OAuth clients persist and keep working **even if the creating user later loses tailnet access** - they belong to the tailnet, not the person, and Admins can see/manage every configured client from the Trust Credentials page.
- **Long-lived auth keys don't exist** (90-day hard cap) - the documented workaround for automation needing keys indefinitely is: create an OAuth client with the `auth_keys` scope, tagged appropriately, and have it **mint new auth keys on demand** via `POST /api/v2/tailnet/:tailnet/keys`, rather than trying to keep one key alive forever.
- **Tag-scoping rule for OAuth-minted auth keys mirrors the ACL tag-hierarchy rule**: the OAuth client's own tag(s) must own (or exactly match) whatever tag the newly minted key requests - same `tagOwners` mechanics as in the ACL/tags raw file. Pattern for one client provisioning multiple device roles: give the OAuth client a broad "owner" tag (e.g. `tag:terraform-tag-owner`) that owns narrower tags (`tag:server`, `tag:database`) in `tagOwners`, then mint keys carrying the narrower tag per use.
- **Direct node registration shortcut**: an OAuth client secret can be passed straight to `tailscale up --auth-key=<secret> --advertise-tags=tag:ci` - Tailscale treats the OAuth secret as a one-shot auth-key-equivalent scoped by the `auth_keys` grant. URL-style parameters can ride along: `?ephemeral=false&preauthorized=true` (ephemeral **defaults to true** in this path, preauthorized defaults to false).
- Devices registered via OAuth client credentials are **always tag-owned** - there is a separate, not-covered-here "device provisioning with OAuth apps" flow specifically for provisioning devices under an individual user's identity instead.
- `get-authkey` CLI utility (Go, requires Go 1.23+) wraps the OAuth-client-mints-a-key pattern for scripting: `go run tailscale.com/cmd/get-authkey@latest -tags tag:development -reusable -ephemeral`.

### Practical automation-credential decision for this stack

For a GitHub Actions CI step (see the ephemeral-nodes raw file) or a one-off provisioning script (Terraform, a deploy hook), an **OAuth client scoped to the minimum needed tags/scopes** is the right default over a raw long-lived auth key, precisely because it's the only mechanism that supports indefinite reuse without a 90-day rotation obligation baked into the credential itself - rotation still matters for the OAuth client secret, but that's a `doppler`-managed secret-value rotation concern, not a network-access-model concern.
