# Customer Portal: what it does, its ceiling, and when to build custom UI instead

- URL: https://docs.stripe.com/customer-management/integrate-customer-portal ; https://adamarant.com/en/blog/stripe-checkout-vs-billing-portal-which-does-what-in-2026 ; https://dev.to/ventureio/stripe-customer-portal-handling-plan-changes-pauses-and-cancellations-without-custom-ui-d1j
- Fetched: 2026-08-14
- Source type: official docs + two community deep-dives (2026), used for the operational webhook-sequencing detail the official doc states more tersely
- Component: Billing Customer Portal vs custom subscription UI

## Facts

- Official integration steps: configure portal features/UI in the Dashboard, implement a redirect (create a Portal Session server-side for an authenticated customer's Stripe customer ID plus a `return_url`, redirect the browser to the session's short-lived `url`), listen to webhooks for subscription/payment-method changes, launch in production.
- The Portal does not authenticate the customer for you, you must authenticate on your own site first, then mint a session tied to that specific `customer` ID. The session URL is short-lived (community sources report ~5 minutes if unopened) and should be generated fresh on click, never cached or reused across page loads.
- Documented ceiling on what the Portal can do without custom code (community-confirmed, cross-checking official Dashboard configuration docs): plan switching in the Portal caps at 10 configurable products/prices; no custom UI injection (branding/logo/toggles only, not layout or extra fields); no built-in signup/acquisition flow (customers always start via Checkout, Payment Links, or your own subscription-creation code, not the Portal); complex flows (metered usage edits, add-ons, quotes, bespoke cancellation surveys, trial extensions, mid-cycle pauses without a subscription schedule) are out of scope and need custom UI backed by the Subscriptions API directly.
- Critical webhook-sequencing gotcha specific to the Portal's cancellation flow (confirmed by both community sources, consistent with subscription lifecycle semantics documented elsewhere): a customer canceling "at period end" in the Portal fires `customer.subscription.updated` with `cancel_at_period_end: true`, NOT `customer.subscription.deleted`. The `deleted` event only fires later, when the subscription actually ends at the end of the current billing period (which can be up to a full billing cycle away). A handler that only listens for `customer.subscription.deleted` to trigger a cancellation confirmation email will send that email weeks late, or never notice the cancellation was requested until access is revoked.
- Practical rule from the same sources: cancellation confirmation email fires on the `subscription.updated` event carrying `cancel_at_period_end: true`; access revocation fires on the later `subscription.deleted` event; these are two distinct actions on two distinct events, not one event doing both.
- Both a Portal-initiated cancel and a direct `stripe.subscriptions.update()`/`.delete()` API call produce the *same* webhook events, a handler doesn't need to know or care whether the change originated in the Portal or your own custom UI; it should react to the event, not the origin.
- Portal is included at no extra platform fee with Stripe Billing; standard processing rates still apply to the underlying charges it manages.
- Design rule this skill inherits: let the Portal own the standard 80% of self-serve billing (card update, invoice history, simple plan switch within the 10-product cap, standard cancel), and build custom UI only for the specific cases the Portal's Dashboard configuration genuinely cannot express, don't rebuild card-update or invoice-history screens by hand.
