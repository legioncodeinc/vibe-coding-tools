# Production failure modes: double-charges, race conditions, missed provisioning

## Facts

- Stripe retries a webhook delivery on any 5xx response or timeout from your endpoint, on an escalating schedule (documented pattern in one source: ~5s, then 30s, then minutes, continuing for up to 3 days), meaning a single real outage on your side can replay the same event a dozen-plus times before you see it succeed.
- Recommended dedup pattern: check a `processedWebhookEvent` (or similarly named) table for `event.id` early; if already present, short-circuit and return 200 immediately without redoing work.
- Counterintuitive but load-bearing detail: mark the event as processed *after* the side effects succeed, not before. If you mark-as-processed first and then crash mid-handler, Stripe will never redeliver (because your dedup check says "already done") and the side effect never completes. If you mark-as-processed last (only on success), a crash mid-handler leaves no processed-row, so Stripe's own retry becomes your free retry mechanism for transient failures, at the cost of a small window where two near-simultaneous retries could both pass the dedup check before either commits.
- Second, independent guard for that small race window: an object-level status guard (e.g., "if order.status is already in a finalized state, refuse to re-finalize it") catches the case where dedup alone misses, belt-and-suspenders, not either/or.
- A named, recurring bug class: reacting to *more than one* Stripe event for the same business outcome. Example: an integration that provisions on both `checkout.session.completed` and `payment_intent.succeeded` for the same order will double-provision even with perfect per-event dedup, because dedup keys on `event.id`, and these are two different events with two different IDs describing (in the integration's mind) "the same" business fact. Rule: pick exactly one Stripe event as the single source of truth per business action, and document the choice so a future change doesn't silently add a second listener for "the same thing."
- Documented real-world break of that rule: a codebase added a `payment_intent.succeeded` handler as a "safety net" alongside an existing `checkout.session.completed` handler for invoice payments, which caused duplicate processing; the fix collapsed both into a single guarded path, but the guard logic (skip `payment_intent.succeeded` whenever certain metadata was present) later silently broke a legitimate direct-PaymentIntent flow that never went through Checkout at all, because that flow had no `checkout.session.completed` event to rely on. Lesson: "pick one event" only works if every code path that reaches a PaymentIntent actually goes through the event you picked; a mixed integration (some flows via Checkout, some via raw PaymentIntents) needs the guard logic to account for both origins explicitly, not assume one.
- Named race condition: client-side "eager sync" (checking/writing state immediately on the browser's return to your `return_url`) racing against the async webhook handler for the same object. Both can read "not yet processed" before either commits, then both write, producing a duplicate credit/fulfillment. Fix pattern: webhooks are the only writer of authoritative payment state; any client-facing "did it work?" check on return should be read-only (poll your own DB, which only the webhook handler ever writes to), never a second code path that also performs the fulfillment side effect.
- Async work scheduled *after* returning the 200 to Stripe (e.g., enqueueing a background job inside the webhook handler) is not protected by the webhook-level dedup table, because the dedup row is written before or alongside the 200, but the background job can still fire again on any Stripe redelivery that arrives before the dedup row is visible, or (separately) if the outbound queue itself doesn't dedup on the same event ID. Fix pattern: write the enqueue into an outbox table in the same DB transaction as marking the event processed, and have a separate worker drain the outbox; this makes the enqueue itself transactionally tied to the dedup guarantee instead of a second unprotected side effect.
- Job-queue-level dedup (e.g., BullMQ's `jobId` deduplication) is only a memory of already-enqueued IDs *while the job still exists in the queue's backing store*; once a completed job is garbage-collected, the same ID can be re-enqueued and will run again. Set the job-retention window to match or exceed Stripe's redelivery window (documented as up to 3 days) so the queue-level guard doesn't expire before Stripe stops retrying; treat your own database-level idempotency check as the real, permanent safety net regardless of queue configuration.
