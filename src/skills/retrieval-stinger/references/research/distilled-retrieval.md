## Postgres full-text search: the lexical arm

Postgres ships two types built for text search, `tsvector` (a normalized, position-carrying document representation) and `tsquery` (a normalized query), matched with `@@` (source: postgres--full-text-search--functions-and-operators-official-docs.md). Building a `tsvector` from a structured document (title, body, tags) uses `setweight` per field, concatenated with `||`, and every field needs `coalesce(field, '')` first because `to_tsvector(NULL)` returns `NULL` and would null out the whole concatenation (source: postgres--full-text-search--controlling-text-search-ranking-official-docs.md).

Four functions build a `tsquery`, and they are not interchangeable: `to_tsquery` requires valid tsquery syntax and throws on malformed input; `plainto_tsquery` and `phraseto_tsquery` normalize plain text but discard punctuation rather than interpreting it; `websearch_to_tsquery` is the only one of the four that can never raise a syntax error, because it treats quotes as phrases, `or` as `|`, a leading `-` as `!`, and ignores everything else. `websearch_to_tsquery` is the only correct choice for a query string coming straight from a user-facing search box (source: postgres--full-text-search--controlling-text-search-ranking-official-docs.md, postgres--full-text-search--functions-and-operators-official-docs.md).

Ranking has two built-in functions: `ts_rank` (frequency-based) and `ts_rank_cd` (cover-density: also weighs how close together the matching lexemes are, at the cost of requiring un-stripped positional data). Both accept a `weights` array matching `setweight` labels (`{D,C,B,A}`, default `{0.1, 0.2, 0.4, 1.0}` so a title hit can outweigh a body hit 10x by default) and an integer `normalization` bitmask controlling how document length discounts the score; normalization bit `32` (`rank/(rank+1)`) is the one that rescales into `[0,1)`, useful when a lexical score needs to sit in the same numeric range as a vector similarity score for downstream blending (source: postgres--full-text-search--controlling-text-search-ranking-official-docs.md). The index for this arm is a GIN index on the `tsvector` column (source: supabase--hybrid-search--reciprocal-rank-fusion-official-docs.md).

## The recall arm: pgvector, owned for storage/indexing by vector-store-stinger

This Stinger owns *recall tuning* over the vector arm (which distance operator, when to weight it up or down, when hybrid beats vector-only), not the column shape or index type, that is `vector-store-worker-bee`'s guide (`vector-store-stinger/guides/pgvector-02-indexing.md` for HNSW vs IVFFlat and operator-class matching). The one fact recall needs from that boundary: whichever operator a query's `ORDER BY` uses (`<->` L2, `<#>` inner product, `<=>` cosine) must match the index's operator class, or the index goes unused and the query silently falls back to a sequential scan (source: supabase--hybrid-search--reciprocal-rank-fusion-official-docs.md, cross-referencing `vector-store-stinger/references/research/raw/neon--pgvector--extension-official-docs.md`).

## Hybrid fusion: Reciprocal Rank Fusion (RRF)

RRF fuses two independently-ranked result lists (lexical, vector) into one list using only rank *position*, not raw score magnitude: a record at rank `r` in a list contributes `1 / (k + r)` to its fused score, summed across every list it appears in; a record absent from a list contributes 0 for that list rather than a penalty (source: supabase--hybrid-search--reciprocal-rank-fusion-official-docs.md). The `k` smoothing constant keeps a rank-1 hit from dominating disproportionately; Supabase's reference implementation defaults `rrf_k=50`, Weaviate's and the wider literature commonly cite `k=60` (source: supabase--hybrid-search--reciprocal-rank-fusion-official-docs.md, weaviate--hybrid-search--fusion-alpha-official-docs.md). RRF's practical property: a record that ranks decently in *both* arms usually beats a record that's #1 in one arm and entirely absent from the other, because summed reciprocal-rank credit rewards cross-arm consistency over a single spike.

The canonical single-query Postgres implementation (source: supabase--hybrid-search--reciprocal-rank-fusion-official-docs.md) runs the lexical arm and the vector arm as two CTEs, each capped at roughly `2x` the final `match_count` so fusion has room to reorder without a full-table scan, joins them with a `FULL OUTER JOIN` on row id (so a record found by only one arm still participates, via `coalesce(..., 0.0)`), and orders by the summed weighted RRF score:

```sql
order by
  coalesce(1.0 / (rrf_k + full_text.rank_ix), 0.0) * full_text_weight +
  coalesce(1.0 / (rrf_k + semantic.rank_ix), 0.0) * semantic_weight
  desc
```

`full_text_weight` / `semantic_weight` are a second, optional tuning lever layered on top of RRF itself, they scale each arm's already-computed RRF contribution, functionally equivalent to this Stinger's legacy `deeplake_hybrid_record(w1, w2)` presets and to Weaviate's single `alpha` scalar (0 = pure keyword, 1 = pure vector, 0.75 = Weaviate's server default) (source: weaviate--hybrid-search--fusion-alpha-official-docs.md). `ts_rank_cd` is explicitly not indexable, it is computed only over the rows that already passed the GIN-indexed `WHERE fts @@ websearch_to_tsquery(...)` filter, so the index still does the heavy narrowing before ranking runs (source: supabase--hybrid-search--reciprocal-rank-fusion-official-docs.md).

Pure rank-position RRF is a documented, known tradeoff, not a defect: Weaviate's own docs show a worked example where their `rankedFusion` (RRF-equivalent) and their `relativeScoreFusion` (min-max score normalization instead of rank position) disagree on the top result, because pure RRF cannot represent "this result dominated one arm by a wide margin" the way score normalization can (source: weaviate--hybrid-search--fusion-alpha-official-docs.md). For most product search, plain RRF over Postgres is the right default because it is simpler, needs no cross-arm score normalization step, and is what the official Postgres/Supabase reference implementation ships; score-normalization fusion is a should-consider upgrade only once a measured case shows RRF misranking a dominant single-arm result.

## Reranking: an optional post-fusion stage

A reranker (Cohere's `rerank-v3.5`/`rerank-v4.0` family is the archived example) takes a query and a candidate list some other retrieval step already assembled and re-sorts it, it does not retrieve, it only reorders (source: cohere--rerank--model-docs-and-v3-5-announcement.md). This makes reranking strictly a *second-stage* refinement: if the fused candidate pool's recall@N is already low, a reranker cannot recover a document that was never retrieved, which is why every evaluation source archived here agrees reranking should be ablated last, after chunking/embedding/fusion are already solid (source: exploreagentic--rag-evaluation--gold-set-component-ablation.md). `rerank-v3.5` combines query + document tokens into one 4096-token budget per document and auto-chunks (rather than truncating or erroring) any document that exceeds it when combined with the query, a real cost/latency variable when deciding how many fused rows to hand a reranker (source: cohere--rerank--model-docs-and-v3-5-announcement.md).

## Chunking strategy

Two independent, methodologically different 2026 benchmarks reach compatible conclusions favoring structural chunking over "smarter"-sounding semantic chunking as the general default:

- The Vectara NAACL 2025 paper (already archived at `.claude/skills/mind-stinger/research/2026-04-25-vectara-naacl-2025-chunking.md`, retrieval-only benchmark): fixed-size recursive character splitting matches or beats semantic chunking across three realistic retrieval tasks and multiple embedders.
- The freshly-archived arXiv 2601.14123 (SPLADE sparse retrieval + Mistral-8B generation, end-to-end with abstention tracking): sentence chunking statistically ties semantic chunking up to ~5k tokens of retrieved context, and both beat plain fixed-size token chunking; semantic chunking's edge over sentence chunking appears only past ~5k tokens (source: arxiv--chunking-strategies--systematic-analysis-reliable-qa-2026.md).

The newer paper's genuinely new findings for this guide, not present in the Vectara source: **overlap measurably did not help** in a sentence-aware, sparse-retrieval setup (|ΔBERTScore| ≤ 0.004, EM deltas ≤ 0.001), while costing `1/(1-overlap)` more chunks to index (20% overlap = 1.25x the chunk count, storage, and embedding cost), recommendation is 0% overlap absent specific contrary evidence for a given retriever. And a **"context cliff"**: retrieval-answer quality rose from small to moderate retrieved-context budgets, then measurably declined past roughly 2.5k tokens in their setup, because excess retrieved context dilutes signal for the generator even when nothing about retrieval itself got worse, the exact cliff point is generator-model-dependent, but a plateau-or-decline point with excess context is described as a general RAG phenomenon, not an artifact of one setup (source: arxiv--chunking-strategies--systematic-analysis-reliable-qa-2026.md). The paper's own practical defaults: sentence chunking, 0% overlap, 150-300 token chunks, ~2.5k token context budget for factual/exact-match tasks, ~500 tokens for summarization/faithfulness tasks.

The citation-backed recommendation for this Stinger's chunking guide, synthesizing both sources: default to structural chunking (sentence-boundary-respecting for prose; the fixed-size-recursive variant is an acceptable, slightly weaker default when a simpler splitter is preferred), skip overlap unless a specific retriever shows a measured benefit from it, and treat semantic (embedding-similarity-boundary) chunking as a documented option for large-context or highly discursive corpora specifically, never as the default "better" choice its name implies.

## Evaluation methodology: recall@k, precision@k, golden query sets

Two 2026 practitioner sources converge on the same structural discipline, generalizing what this Stinger's pre-existing Deep-Lake-specific evaluation guide already taught for one recall pipeline into a methodology for a multi-component Postgres pipeline:

**Split retrieval from generation, and diagnose which stage failed** before touching anything. Retrieval evaluation is a pure information-retrieval problem (deterministic, no LLM needed, graded against labeled relevant chunks); generation evaluation needs an LLM judge and is only meaningful once retrieval is trusted (source: aisuffer--rag-evaluation--recall-precision-golden-set.md, exploreagentic--rag-evaluation--gold-set-component-ablation.md).

**The metric set**: recall@k (of all relevant chunks, what fraction landed in the top k, "gates everything," per both sources, since a downstream metric is moot if the relevant chunk was never retrieved), precision@k (of the top k, what fraction is actually relevant, noise that costs tokens and raises hallucination risk), MRR (rewards the first relevant hit ranking early), nDCG@k (graded relevance with position discounting, for when relevance isn't binary). Recall@k first, always, tune k to the actual context budget the generator will receive, then optimize recall at that k before touching ranking (source: both eval sources).

**Golden set construction**: real production queries, not brainstormed or purely synthetic ones (synthetic/LLM-generated queries are acceptable for bootstrapping volume but are systematically easier, since they were written by reading the answer); human-labeled relevant chunks per query; and, the concrete addition from Explore Agentic not present in the Deep-Lake-specific guide, deliberate **hard negatives** (topically close but wrong chunks) to separate a reranker that actually helps from one that just reshuffles already-obvious results. Sizing guidance: a focused 150-300 query set, stratified across single-fact/multi-hop/comparative/ambiguous types, beats a much larger unstratified or unlabeled set; report per-stratum scores, never just a global average, since the average hides exactly the multi-hop collapse that matters most (source: exploreagentic--rag-evaluation--gold-set-component-ablation.md).

**Component ablation** is the procedure for a multi-stage Postgres pipeline (chunker, embedding model, full-text arm, RRF fusion, optional reranker) that the single-mode Deep-Lake pipeline never needed: change one component at a time, held against the fixed gold set, and ablate in pipeline order, recall-affecting components (chunking, embedding, hybrid fusion) before ranking-only components (reranker), because a reranker measured against a low-recall candidate pool looks falsely useless (source: exploreagentic--rag-evaluation--gold-set-component-ablation.md).

**Before/after discipline carries over unchanged** from the Deep-Lake-specific guide: no metric snapshot before a pipeline change means no evidence the change helped, and "feels better" was never a measurement.

## Open questions carried forward

- No first-party benchmark was archived for `ts_rank_cd` cost at scale on a large `tsvector` column relative to a GIN-indexed prefilter; the Supabase reference implementation notes it is "not indexable" and relies on the `WHERE ... @@ ...` filter to keep the ranked set small, but no source here quantifies the ranking cost itself at high row counts.
- The RRF `k` constant varies by source (Supabase's own reference function defaults to 50; the wider literature, including Weaviate, commonly cites 60) with no archived source explaining the numeric difference; treat both as reasonable, low-sensitivity defaults rather than a settled constant, and sweep it on a labeled set if fusion ranking quality is in question.
- The arXiv chunking paper's "context cliff" point (~2.5k tokens) was measured on one generator (Ministral-8B-Instruct-2410) and explicitly flagged by its own authors as needing re-tuning per generator model; no source archived here re-validates that cliff point against a different generator class.
