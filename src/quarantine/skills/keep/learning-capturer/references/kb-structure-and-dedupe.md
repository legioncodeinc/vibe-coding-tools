# Knowledge base structure and deduplication

Where the artifact lives, what shape it has on disk, and what happens when the same wall
gets hit twice.

---

## 1. The layout

```
knowledge-base/
├── INDEX.md                 generated by scripts/kb_index.py, never hand-edited
├── entries/
│   ├── 2026-07-09--vercel-edge-fs-module-not-found.md
│   ├── 2026-07-22--prisma-p3009-neon-branch-reset.md
│   └── ...
├── open-walls.md            problems abandoned, not solved. One line each.
└── rejected.md              candidates the user declined. The rejection ledger.
```

Flat `entries/`, one file per entry, filename equal to the entry `id`. No topic
subdirectories.

**Why flat rather than the topic-tree layout the archive describes.** The only concrete
personal knowledge base layout in the archive uses one directory per major topic with an
`index.md` in each, aiming to be "just organised enough without having a crazy directory
tree structure" [research/distilled-personal-knowledge-capture.md section 7]. That source
explicitly does not solve search: its layout is browsable, not indexed, and it offers no
answer to finding an entry by a remembered error string months later
[research/distilled-personal-knowledge-capture.md section 7].

The retrieval path here is a human running grep for an error string, not a human browsing.
Topic folders help browsing and hurt grep, because they force a filing decision at write
time about a category the user will not remember at read time. That is the same failure the
practitioner source repaired by abandoning topic grouping in favor of indexing by future
retrieval context [research/distilled-personal-knowledge-capture.md section 2]. Tags carry
the topic dimension instead, and the generated `INDEX.md` carries browsing.

**Flat plus tags plus a generated index is a design decision** filling a gap the archive
names but does not fill [research/distilled-personal-knowledge-capture.md section 8].

### Why plain markdown in a directory

Portability, since this "removes the reliance on proprietary sites"; durability, since
"each copy of the repo is just the same as any other"; freedom from any particular standard;
and low formatting effort for code snippets, links, and tables
[research/distilled-personal-knowledge-capture.md section 7]. Markdown is chosen because it
"is familiar to a large proportion of developers, is easy to write, and widely-supported"
[research/distilled-personal-knowledge-capture.md section 7].

Put `knowledge-base/` under version control if the user wants history. Do not require it.

### Where it goes

Ask the user once, on first run, and record the answer. Default to `knowledge-base/` in the
working directory. Never scatter entries across multiple locations, and never write into a
location the user did not name.

## 2. Making it greppable

The retrieval path is: months later, an error appears, the user pastes part of it into
grep or into their editor's project search. Everything below serves that one path.

**The `SEARCH:` line.** Every entry carries exactly one, holding the literal error string
on a single unwrapped line. That is the primary grep target:

```
grep -ri "P3009" knowledge-base/entries/
grep -rn "SEARCH:" knowledge-base/entries/
```

Rules that keep this working:

1. **One line, never wrapped.** A wrapped error string does not match a pasted error string.
2. **Verbatim.** No smart quotes, no ellipsis, no trimming to fit.
3. **One `SEARCH:` line per entry.** Where an error has several surface forms, put the
   others under `Also searched as:`, which is also greppable and is not the primary key.
4. **Case as captured.** Grep with `-i` covers the rest.

**Filename as a second index.** `YYYY-MM-DD--kebab-slug.md`, where the slug is built from
the symptom, not the cause. `ls entries/ | grep migrate` should work.

**Tags as the third.** Lowercase kebab, comma-separated on one line in the metadata block,
so `grep -l "tags:.*neon" entries/*.md` works. Keep a controlled vocabulary: the tool or
service, the layer, and the failure class. Three to six tags. Tag drift is what makes tags
useless, so `kb_index.py` prints the tag histogram on every run and near-duplicate tags
show up immediately as two entries where there should be one.

**INDEX.md.** Generated, one row per entry: id, title, tags, occurrences, last-seen,
staleness flag. It is for browsing and for spotting recurrence at a glance. It is
regenerated, never edited, and it is the thing to open when the user asks "what is in
here".

## 3. The dedupe decision

Runs before any candidate is drafted, and again before any entry is appended. A knowledge
base full of near-duplicate entries is the same failure as one full of unprocessed
collected material: it accumulates faster than it can be engaged, becomes unmanageable, and
is then ignored [research/distilled-personal-knowledge-capture.md section 2]. The archived
example became unmanageable at roughly 2,000 notes
[research/distilled-personal-knowledge-capture.md section 2].

**All thresholds below are design decisions, not researched practice. The archive contains
no research on deduplicating entries in a personal knowledge base**
[research/distilled-personal-knowledge-capture.md section 8]. Tune them against the user's
actual base.

### The check

Run the script first:

```
python3 scripts/kb_index.py knowledge-base --check "<the literal error string>"
```

It normalizes and compares the candidate string against every `SEARCH:` line and title in
`entries/`, and prints scored candidates with their ids. It matches text, not meaning, so
it is a first pass.

Then judge on three axes, in this order:

| Axis | Question |
|---|---|
| **Symptom** | Is the error string the same, allowing for interpolated paths, ids, and numbers? |
| **Cause** | Is the mechanism the same, where both are established? |
| **Fix** | Does the existing entry's fix resolve the new occurrence? |

### The rule

| Symptom | Cause | Fix works | Action |
|---|---|---|---|
| Same | Same | Yes | **Update.** Add an occurrence row. Nothing else changes unless the context differs. |
| Same | Same | No | **Update.** Add an occurrence row AND a new variant section under The fix, ordered by likelihood, most common first [research/distilled-personal-knowledge-capture.md section 3]. |
| Same | Different | No | **New entry.** Cross-link both under Related, and say in each that the symptom is shared. This is the case the reader most needs warning about. |
| Different | Same | n/a | **New entry**, cross-linked. Symptom is the retrieval key, so a different symptom needs its own key. |
| Same, but only after normalizing away a path or an id | Same | Yes | **Update.** Generalize the `SEARCH:` line to the invariant part and move the specific value into the fenced block. |

**When it is ambiguous, update rather than create.** A slightly over-broad entry is
recoverable by splitting it later. Two near-identical entries are not, because the user will
find one, act on it, and never learn the other existed.

### Normalizing before comparing

Strip before you compare: absolute paths, line and column numbers, UUIDs and hashes, port
numbers, timestamps, memory addresses, and process ids. Two errors that differ only in
`/Users/<name>/projects/a` versus `/b` are the same error.

Do not strip: version numbers, error codes, exception class names, package names. Those are
the discriminators.

### Scrub before you compare

Run the scrub in `secret-scrubbing.md` **before** any candidate string is passed to the
dedupe check or printed in a report. A connection string in an error message is a secret
that is about to be echoed into a comparison, a report, and possibly a file. Never let a
matched secret reach the transcript.

## 4. Updating an existing entry

An update touches exactly these fields:

1. Append a row to **Occurrences**: date, receipt, and what was different this time.
2. Bump `last-seen` and `occurrences` in the metadata block.
3. Set `last-confirmed` to today, since the fix was just demonstrated to still work. See
   `staleness-and-versions.md`.
4. Add the new versions to **Context** if the stack moved, as a second row rather than
   overwriting the first. A fix that worked on two versions is more valuable than a fix
   whose history was erased.
5. Add to **What did not work** if the new occurrence produced new dead ends.
6. Add a fix variant only where the original fix did not work this time.

Do not rewrite the Root cause on an update unless the new occurrence actually established
it. If it did, change `root-cause-status` from `empirical` to `established` and say what
established it.

**Never silently overwrite.** Every update is shown to the user as a diff of these fields
before it is written, same as a new entry.

## 5. Recurrence is a signal, and it escalates

The point of the occurrence log is not bookkeeping. Google's postmortem practice runs
automated trend analysis across many postmortems precisely so that recurrence across records
becomes visible [research/distilled-personal-knowledge-capture.md section 4]. The personal
version is this ladder.

| Occurrences | What the sweep report says |
|---|---|
| 1 | Nothing. It is an entry. |
| 2 | Note it in the report. "Second time, first was <date>." |
| 3 | Flag it. Name the elapsed span and the summed time-cost lower bounds. Ask whether the underlying condition can be removed rather than re-fixed. |
| 4 or more | Escalate to the top of the report as its own item, above new candidates. Propose the structural fix explicitly: a pinned version, a lint rule, a CI check, a template, a removed dependency, a changed default. |

Wording for the 4-or-more case, adapted to the entry:

```
RECURRING: you have hit this four times since 2026-03-11 (3/11, 5/02, 7/09, 8/14).
Lower-bound time spent across all four: at least 2h35m. The fix is the same every
time. Consider removing the condition instead: <the specific structural change>.
```

Keep it blameless. A record that indicts the person reading it stops getting written
[research/distilled-personal-knowledge-capture.md section 4]. "You have hit this four
times, here is the structural fix" is the tone. Not "you keep making the same mistake".

**The escalation is a proposal, never an action.** This skill does not change the user's
code, pin their versions, or add CI checks. It writes the recommendation into the report.

## 6. open-walls.md

Abandoned problems, one line each. Not fix entries. See `solve-detection.md` section 3.

```markdown
# Open walls

Problems that stopped appearing without being solved. No fix is recorded because none was
found. A wall that shows up here more than once is a candidate for real time.

| Date | Symptom | What was tried | Receipt |
|---|---|---|---|
| 2026-06-03 | Playwright CI run times out on the auth fixture, passes locally | headed mode, longer timeout, retry x3 | [Tue, June 3, 2026 10:14 EDT] |
```

If the same wall later gets solved, the line moves out of `open-walls.md` and becomes a full
entry whose Occurrences table backfills the abandoned encounter. Say so in the report.

## 7. rejected.md, and why a rejection is permanent

When the user declines a candidate, it is recorded here with the date and, where they gave
one, the reason. **A rejected candidate is never proposed again.**

```markdown
# Rejected candidates

Do not re-propose anything on this list. Matching is on the normalized symptom string.

| Date rejected | Symptom | Reason | Fingerprint |
|---|---|---|---|
| 2026-08-15 | npm WARN deprecated inflight@1.0.6 | not a real problem | npm-warn-deprecated-inflight |
| 2026-08-15 | 401 from the staging API | one-off, expired token, nothing to learn | 401-staging-api-expired-token |
```

The fingerprint is the normalized symptom slug and is what the dedupe check matches on.
Check `rejected.md` at the same point in the flow as `entries/`, on every run, before
drafting anything.

Re-proposing something the user already said no to is the fastest way to get the weekly
routine muted, and a muted routine is a dead knowledge base. Rejection is cheap to honor
and expensive to ignore.

### Keeping the routine in step

The routine cannot read `rejected.md`, because a routine has no filesystem. It has two other
memories, and both are used:

1. **Its own past reports**, via `LB_INTERNAL_GET_ROUTINE_REPORTS`. Every sweep report ends
   with a carry-forward block listing every rejected fingerprint to date. Each new report
   copies that block forward and appends anything new. That is what makes the routine's
   memory cumulative rather than five-reports-deep.
2. **Its own prompt.** After the user rejects a candidate in a Cowork session, offer to
   append the fingerprint to the routine's standing do-not-propose list. Call
   `LB_INTERNAL_GET_ROUTINE_CONFIG` first, because `prompt` REPLACES the whole prompt on
   update (`littlebird-mcp-reference.md`, routine tools). Then call
   `LB_INTERNAL_UPDATE_ROUTINE` with the full revised prompt. Show the user the revised
   prompt text and get approval before calling it.

Use route 2 for anything rejected as permanently uninteresting. Use route 1 alone for
one-off rejections. The prompt has finite room, so do not push every rejection into it.
