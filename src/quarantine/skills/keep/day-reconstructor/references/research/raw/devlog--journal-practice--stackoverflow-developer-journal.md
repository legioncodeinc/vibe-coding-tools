## What a journal is, per this source

"a place to define the problem you're solving and record what you tried and what worked."
Framed as a private tool for organizing thought at the code level, deliberately distinct
from a project management tool.

## What it should contain

- Daily goals and daily recaps.
- Problem definitions and implementation plans.
- Uncertainties and hypotheses.
- Attempted solutions and their outcomes.
- Ideas, questions, and side tasks.
- Emotional reactions and anxieties.
- Retrospectives on finished work.

## On debugging specifically

The instruction when stuck: "jot down everything you tried so far."
The instruction on resolution: "jot down the solution or logic that got you there."

This is the exact record structure the skill's problem-solved section reconstructs from
capture: the error, the attempts, the resolution.

## Claimed benefits

- Better focus, through reduced cognitive load.
- Better code, through clearer problem definition before starting.
- Professional growth, through reflection on struggles and successes.
- Fewer context switches and less sidetracking.
- Better one-to-ones, performance reviews, and team communication.
- Documentation that supports career advancement.

## Why the habit fails

One failure mode named: "Don't fall into the trap of setting up a system for hours only to
abandon it once you start going, like buying the nicest journal only to realize you don't
want to write regularly."

The identified enemy is setup cost and the daily writing burden, not disagreement about
value. That is a direct argument for automating the capture side.

## Format and cadence advice

- Write at the start and the end of each session, daily.
- Use a text editor rather than paper, for linkability and for pasting code.
- Keep the writing standard deliberately low: "Don't worry about sounding smart or being
  neat. Nobody's grading you."
- "your journal is customizable."
