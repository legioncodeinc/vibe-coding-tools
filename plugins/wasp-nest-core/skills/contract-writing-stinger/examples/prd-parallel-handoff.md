# Example: export request status shared by two PRDs

This synthetic example shows a proposed boundary becoming a reusable agreement. It is not a real accepted decision for any repository.

`CTR-004-export-request-status.md` names the backend status endpoint as provider and the account settings screen as consumer. It defines `GET /api/export-requests/{id}`, a JSON response with a required `status` enum (`pending`, `processing`, `ready`, `failed`), a nullable `downloadUrl` that is non-null only when `status` is `ready`, and a `404` when the request is not visible to the current user. It links the API schema, names ownership of provider and consumer checks, and explains how an older UI handles a new optional response field. [../references/research/raw/openapi-specification.md](../references/research/raw/openapi-specification.md) [../references/research/raw/json-schema-specification.md](../references/research/raw/json-schema-specification.md)

Until Mario accepts the exact revision, the record stays `Draft`. The backend and UI sub-PRDs may draft local details, but neither can be finalized against unsettled shared terms. After acceptance, both PRD authors pin `CTR-004` revision 1 in `## Contract dependencies` and finish their documents independently. The later implementations have the same endpoint, states, errors, and verification obligations. A subsequent change to `downloadUrl` requiredness needs a new CTR record that supersedes CTR-004; completed historical PRDs retain their CTR-004 pin.
