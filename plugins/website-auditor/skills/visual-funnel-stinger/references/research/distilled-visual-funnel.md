Dense reference distilled from `raw/`. Every claim below cites its source file in brackets. Organized around this Bee's actual job: a real-browser, desktop-plus-mobile, 25-page-depth walk of the customer funnel with screenshots at checkpoints, run in wave W5 and reading `02-positioning/` for the funnel definition, that stops short of any state-creating action (a real purchase, a submitted lead form) unless interactive/stateful mode has been explicitly opted into for that run. ## 1. What kind of audit this is (and is not)

- A UX audit is defined as a structured, evidence-based evaluation of a product's experience against real user behavior, usability heuristics, and business goals, explicitly framed as diagnosis, not redesign. [raw/www-wowmakers-com-blog-ux-audit.md]
- The same source draws a three-way distinction that maps directly onto how this Bee's own walk should be understood: a UX audit is the holistic expert review of the whole experience against heuristics, data, and goals (used when you sense UX is costing conversions but cannot pinpoint where, output is prioritized findings plus a roadmap); usability testing is watching real users attempt real tasks (used when you need evidence on a specific flow or hypothesis, output is observed task success or failure); heuristic evaluation is scoring an interface against fixed principles such as Nielsen's ten (a fast, low-cost expert pass, often used as one lens inside a fuller audit). A full audit typically contains a heuristic evaluation and may commission usability testing, but is broader than either alone. [raw/www-wowmakers-com-blog-ux-audit.md]
- A CRO audit is defined as a structured diagnosis of why visitors who could convert do not, and the source is explicit about what it is NOT: not a redesign brief, not a screenshot tour of competitor sites annotated with best-practice violations, not "opinions about design trends" or "heuristics applied without evidence." Its stated output is a prioritized backlog of testable hypotheses, each tied to evidence, each with a defined way to measure whether the change worked. [raw/junto-fr-en-blog-cro-audit.md]
- The ecommerce-specific framing of the same discipline: an ecommerce CRO audit is "a structured review of your store's conversion funnel, walked in purchase order: traffic intent, product or landing page, cart, checkout," with the output being "a prioritized list of leaks, each tied to a benchmark and a fix," not a list of opinions. The source stresses that the word doing the work is "order": most audits start at the homepage hero and never reach checkout, which is backwards, because ecommerce loses most of its money after the add-to-cart click, not before it. [raw/www-pages-report-blog-ecommerce-cro-audit.md]
- All sources converge on the same underlying discipline regardless of label ("UX audit," "CRO audit," "landing page audit," "ecommerce CRO audit"): evidence and order before opinion, and a walk of the actual pages sequenced deliberately rather than starting wherever is most visually interesting. [raw/junto-fr-en-blog-cro-audit.md] [raw/www-wowmakers-com-blog-ux-audit.md] [raw/www-pages-report-blog-ecommerce-cro-audit.md] [raw/www-apexure-com-blog-landing-page-audit-checklist.md]

## 2. Why a page walk needs to be sequenced after a data-trust check

- The CRO-audit source's central structural claim, and the one most directly relevant to how this Bee should treat any quantitative signal it is handed (traffic, conversion counts, analytics from other Bees): "if your conversion rate is computed from broken inputs, every heatmap insight and every funnel analysis inherits the error." The source frames analytics validation as step one, before any page-level judgment, on the reasoning that skipping it invalidates everything downstream. [raw/junto-fr-en-blog-cro-audit.md]
- Concrete checks the source runs before trusting funnel data: whether "conversion" is consistently defined across the team; duplicate or phantom events (purchases firing on refresh, double-counted form submissions, thank-you pages reachable from stale email links); consent-banner-driven data loss, which the source notes is not randomly distributed across users; cross-domain and payment-provider redirects breaking session attribution; and a back-office reconciliation check (do analytics transactions match the order database) described as "the single most revealing test." [raw/junto-fr-en-blog-cro-audit.md]
- Illustrative case cited: rebuilding the measurement layer for one client (an online learning platform) multiplied the observed opt-in rate by seven and raised tracked conversions 34%, with the underlying site unchanged, only the measurement of it. The point drawn from this example is that an audit run on bad data would have chased a conversion problem that was actually a measurement problem. [raw/junto-fr-en-blog-cro-audit.md]
- Consistent with this, the ecommerce-CRO source insists on benchmarking before auditing anything, and warns against comparing the wrong benchmark to the wrong traffic: sitewide ecommerce conversion (all visitor types mixed, cited at 2.74% globally, mobile 2.86%, desktop 2.46%, source: Dynamic Yield as of August 2026) is a different number from dedicated-landing-page conversion (visitors who clicked one campaign and hit a page built for one offer, cited at a 4.2% median, ranging from 1.3% for fashion and beauty up to 7.1% for food and beverage, source: Unbounce CBR, Q4 2024). Comparing a store's ad-landing-page rate against the sitewide figure, or vice versa, produces a false "leak" finding. [raw/www-pages-report-blog-ecommerce-cro-audit.md]
- Practical implication for this Bee: because it runs downstream of (or alongside) other Bees rather than owning analytics validation itself, any funnel-stage drop-off number or benchmark it is handed should be treated as provisional evidence to corroborate visually, checked against the right comparison class (sitewide vs. landing-page-specific, vertical-specific), not as ground truth to build a finding on alone. This is an inference drawn from the sources' stated frameworks, not a claim any source makes about this plugin specifically.

## 3. Research methods that inform where to look before screenshotting

- Heatmaps and scroll maps: read for anomalies, not confirmation. Named useful patterns: clicks landing on elements that are not actually clickable (a sign users expect an interaction that is not there), heavy interaction on elements that lead nowhere useful, and scroll maps showing that content answering a visitor's main objection sits below where most visitors stop scrolling. The source's own example: a pricing answer at 80% scroll depth on a page where attention dies at 50% is called a finding; a hot spot on the main CTA is explicitly called NOT a finding (i.e., not surprising enough to act on). [raw/junto-fr-en-blog-cro-audit.md]
- Session replays: the discipline is sampling by failure cohort, not watching random sessions. Named examples of useful cohorts: visitors who reached checkout and left, or mobile users who spent over a minute on a form. The source claims watching random sessions "produces anecdotes," while watching failure cohorts "produces patterns," citing examples like a coupon field that sends people off-site to hunt for a code, an error message rendering off-screen on mobile, or a date picker that resets on validation errors. [raw/junto-fr-en-blog-cro-audit.md]
- User intent signals: on-site search queries (revealing vocabulary gaps between navigation and how customers actually think), post-purchase or exit surveys, and support-ticket/sales-call themes. The source's example: if visitors keep asking about delivery times in chat, the funnel has a delivery-time problem regardless of what click data shows. This research layer is also framed as protection against optimizing a page for the wrong traffic intent (a comparison-stage ad landing page needs different content than the same URL receiving brand-search traffic). [raw/junto-fr-en-blog-cro-audit.md]
- The WowMakers source names an adjacent method, the cognitive walkthrough (stepping through a task as a first-time user), as an alternative lens to heuristic evaluation, distinct from but complementary to the CRO source's heatmap/replay/intent methods. [raw/www-wowmakers-com-blog-ux-audit.md]
- The Apexure landing-page source adds a scroll-map-derived finding of its own: its Hotjar scroll-map data across 60 of its own blog posts is cited as informing CTA placement frequency (checking for a CTA after each major section), though the archived fetch is cut off before stating the specific quantitative finding. [raw/www-apexure-com-blog-landing-page-audit-checklist.md]

## 4. Funnel-stage friction mapping: general framework plus ecommerce-specific detail

- The CRO-audit source's friction inventory is explicitly sequenced last, after the data-trust check and the behavioral research layer, described as a "systematic walk through the funnel, logging every point of friction against the evidence gathered" in the prior step, done stage by stage specifically to keep the inventory honest and anchored to measured drop-off points rather than to whichever pages are most interesting to critique. For an e-commerce funnel this source names Entry (does the landing experience match the promise that brought the visitor; message mismatch between ad and page is called one of the most common and most fixable sources of bounce) and Discovery (category pages, filters, on-site search), but the archived text cuts off mid-description of the second stage and does not reach any stage past it. [raw/junto-fr-en-blog-cro-audit.md]
- The round-3 ecommerce-CRO source fills this gap directly with a five-step, purchase-ordered walk (product/landing page, cart, checkout, then speed as a funnel-wide multiplier), each step anchored to a named benchmark rather than opinion:
  - **Product/landing page.** Check message match to the referring ad/search query; price and total-cost clarity (surface shipping expectations on the product page, not three steps later); proof (reviews, ratings, guarantees) above the fold or one scroll away; and a single primary action (Add to Cart), with everything else visually secondary. Ecommerce-specific move: rank product templates by revenue exposure (sessions x price) and audit the top three first, not the homepage. [raw/www-pages-report-blog-ecommerce-cro-audit.md]
  - **Cart.** Framed as a decision checkpoint, not a renegotiation point. Baymard Institute's running meta-analysis of 50 studies puts average cart abandonment at 70.22%, though 42% of US abandoners were "just browsing" and not a fixable leak. Fixable checks: full estimated total (shipping and tax included) shown before checkout starts; quantities/removal editable without page reloads or dead ends; cart reachable and persistent, especially on mobile; and upsells not pushing the total further from what the buyer expected. [raw/www-pages-report-blog-ecommerce-cro-audit.md]
  - **Checkout ("this is where the money dies").** Baymard's ranked reasons US shoppers with real purchase intent abandoned checkout: extra costs too high (40%), delivery too slow (20%), didn't trust the site with card information (19%), forced to create an account (18%), checkout too long or complicated (17%), site errors or crashes (17%). The source reads this table as the checkout audit itself, in priority order: audit where shipping cost first appears in the funnel (if only at the last step, that is the single biggest fixable leak; test a "free over $X" threshold stated on the product page); show a delivery estimate before payment, not in the confirmation email; use recognized payment badges and familiar payment options with no visual jank on the payment step; offer guest checkout, full stop, asking for an account only after the order; and count form fields, then complete a real purchase on the store, on a phone, on mobile data. The source explicitly notes what is absent from this list: hero copy, brand fonts, homepage carousels, nearly every real reason is operational, which is why an audit weighted toward the top of the funnel misses most of the recoverable revenue. [raw/www-pages-report-blog-ecommerce-cro-audit.md]
  - **Speed as a funnel-wide multiplier.** Cited Portent data: 3.05% conversion at a 1-second load versus 0.67% at 4 seconds (the archived fetch cuts off before the 2-second and 3-second data points survive). [raw/www-pages-report-blog-ecommerce-cro-audit.md]
- The Apexure landing-page source supplies a parallel, non-ecommerce-specific but directly complementary above-the-fold checklist for the entry stage specifically, organized as a table of checkpoint / what-to-check / common-failure: headline clarity (value prop under 10 words), ad-to-page message match, hero image relevance (reinforces the offer versus decorative stock), CTA visibility without scrolling on any device, load time (LCP under 2.5s for the largest above-fold element), and at least one trust signal visible above the fold. Its own project history attributes roughly 40% of all audit findings to above-the-fold issues specifically, and cites message mismatch as the single most common conversion killer, appearing in over half of the audits it runs, illustrated by a cited case where fixing a Google-Ads-to-headline mismatch took a page from 1.02% to 6.09% conversion (a 500% increase, confirmed by A/B test). [raw/www-apexure-com-blog-landing-page-audit-checklist.md]
- The same source's copy/messaging and CTA checkpoints, useful as landing-page-specific detail this Bee can apply at the Entry stage: benefit-to-feature ratio no worse than 2:1, a scan-ability test (can the offer be understood from headline + subheads + CTA text alone), specificity over vague claims, objection-handling for the top 2-3 objections of the target audience, Grade 6-8 reading level; and for CTAs, minimum 4.5:1 button contrast ratio, action-specific button copy over generic ("Submit" is cited as converting roughly 3% worse than an action-specific phrase like "Get My Free Quote"), and a single primary action per screen. [raw/www-apexure-com-blog-landing-page-audit-checklist.md]

## 5. Chrome/Playwright device-emulation conventions for automated screenshot capture

- Playwright's official device-emulation model is a registry (`playwright.devices`) of named device descriptors that bundle `userAgent`, `viewport`, `deviceScaleFactor`, `isMobile`, and `hasTouch` together; the idiomatic pattern is spreading one descriptor into a browser context or into a test-runner project's `use` block (`...devices['Desktop Chrome']`, `...devices['iPhone 13']`), rather than setting each field by hand. [raw/playwright-dev-docs-emulation.md]
- `viewport` is included in the device descriptor but can be overridden per-test or per-context with `page.setViewportSize()`; the official docs flag that when both a descriptor and an explicit `viewport` are set, the `viewport` property must be defined AFTER destructuring the device object in code, since the descriptor itself also defines a viewport and would otherwise silently win or lose depending on declaration order. Beyond viewport, `locale`, `timezoneId`, `permissions`, `geolocation`, `colorScheme` ('light'/'dark'), and `userAgent` are all independently overridable emulation fields on top of a device descriptor. [raw/playwright-dev-docs-emulation.md]
- `isMobile` specifically controls whether the page honors the meta viewport tag and whether touch events are enabled; like `viewport`, it must be set after destructuring a device descriptor if it is being overridden. [raw/playwright-dev-docs-emulation.md]
- The official docs separately flag that pre-configured device descriptors assume a specific host platform for their user-agent string (for example, "Desktop Chrome" ships a Windows-specific user agent regardless of what OS the automation actually runs on), and recommend setting `userAgent: undefined` after spreading a descriptor to fall back to the real host platform's UA string when that specificity is undesirable. [raw/playwright-dev-docs-emulation.md]
- Direct implication for this Bee's stated 1440x900 desktop / 390x844 mobile capture convention: neither of those two viewport sizes matches any single named Playwright registry descriptor exactly (the registry's desktop entries commonly use 1280x720, and the closest stock mobile descriptors cluster around iPhone-model viewports in the 390-430 width range at a 2-3x device scale factor, not 390x844 specifically), so this Bee's capture setup is best implemented as an explicit custom context configuration (setting `viewport: { width: 1440, height: 900 }` for desktop and `viewport: { width: 390, height: 844 }` plus an explicit mobile `userAgent`, `deviceScaleFactor`, and `isMobile: true`/`hasTouch: true` for mobile) rather than a bare spread of an off-the-shelf named device descriptor. This is a reasoned inference from the registry's documented mechanics, not a claim sourced from any raw file stating "390x844" by name.
- Full-page screenshot capture with `toHaveScreenshot()` or `page.screenshot()` is documented as sensitive to the host OS, browser version, settings, hardware, power source, and headless-vs-headed mode; the official guidance for reproducible screenshots is to run capture in the same environment used to generate any baseline being compared against. This is a visual-regression-testing feature (compare against a stored baseline) rather than a one-shot audit-capture feature, so it is only partially applicable to this Bee's use case of capturing fresh screenshots per audit run rather than diffing against a committed baseline; the determinism caveat about host environment still applies to any screenshot this Bee takes. [raw/playwright-dev-docs-emulation.md]
