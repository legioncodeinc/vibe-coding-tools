# Distilled audit-scoring research

Dense reference distilled from `raw/`. Every claim below cites its source file in brackets. This Bee needs a multi-level (leaf finding to sub-audit to category to final score) weighted rollup engine that is N/A-aware (a criterion that doesn't apply must be excluded from a weighted average without corrupting the weight-sums-to-1 constraint), rendered into a branded, formula-driven XLSX deliverable via Python (openpyxl or similar). The round-2 archive covered the core weighted-rollup formula (SUMPRODUCT) and general spreadsheet-integrity practices from two adjacent-but-different domains (RFP vendor evaluation, portfolio project prioritization). This round-3 sweep closes three previously-flagged gaps with real technical sources: (a) N/A-aware SUMPRODUCT formula mechanics, (b) generating branded/styled XLSX reports programmatically via openpyxl, and (c) multi-level rollup/rubric scoring engine design. Where a gap still isn't fully closed by what was found, that is stated plainly rather than invented.

## 1. The core weighted-rollup formula: SUMPRODUCT

Four sources across both research rounds converge on SUMPRODUCT as the mechanic for turning a row of per-criterion scores and a row of weights into one weighted total, the direct analogue of this Bee's leaf/sub-audit rollup arithmetic:

| Detail | legalclarity.org | portfoliohub.io | exceljet.net | datacamp.com |
|---|---|---|---|---|
| Formula shape | `=SUMPRODUCT(scores_range, weights_range)` returns "a single weighted total per vendor" | `=SUMPRODUCT($D$2:$H$2,D4:H4)`, weights in row 2 as decimals, scores in row 4+; returns 1 to 5 and "keeps working if you reorder the criteria" | `=SUMPRODUCT(weights,values)/SUM(weights)`, generic form; worked example uses a named range `weights` rather than plain cell references | `=SUMPRODUCT(values, weights) / SUM(weights)`; documents the underlying mechanics (array-shape matching, blanks treated as zero, text ignored) |
| Divide-by-sum-of-weights | Not shown; assumes weights already sum to 1 | Not shown directly, but a separate weight-check formula enforces sum-to-1 | Explicit: `/SUM(weights)` makes the formula correct even when weights do NOT sum to 1, since a non-1 sum simply becomes a non-1 divisor that self-corrects the result | Same explicit `/SUM(weights)` divisor pattern |
| Source | [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md] | [raw/portfoliohub-io-blog-project-prioritization-template.md] | [raw/exceljet-net-formulas-weighted-average.md] | [raw/datacamp-com-tutorial-sumproduct.md] |

All four are vendor/community-tier sources of roughly equal authority; none conflicts with another on the core mechanic. The `/SUM(weights)` divisor pattern (exceljet, datacamp) is a strictly more robust formula than the bare `SUMPRODUCT(...)` used in the two round-2 sources, since it self-corrects if weights don't sum to exactly 1 (a documented common defect per portfoliohub: "weights that quietly sum to 1.15"), and is the form this Bee's rollup engine should prefer. [raw/exceljet-net-formulas-weighted-average.md] [raw/datacamp-com-tutorial-sumproduct.md] [raw/portfoliohub-io-blog-project-prioritization-template.md]

Additional rollup/ranking mechanics from the portfolio-prioritization source: `=RANK(I4,$I$4:$I$40)` for ranking by weighted score (highest ranks 1); `=SUMIFS($J$4:$J$40,$L$4:$L$40,"<="&L4)` to compute a cumulative running total down a ranked list without physically sorting the sheet; and a mandatory weight-check formula, `=SUM($D$2:$H$2)`, which must equal 1. [raw/portfoliohub-io-blog-project-prioritization-template.md]

## 2. N/A-aware weighted formulas: the previously-unfilled gap, now closed

This is the core technical gap flagged going into this round: neither round-2 source addressed how a SUMPRODUCT-style formula behaves when a criterion does not apply. Two round-3 sources close it with a concrete, general mechanism.

| Mechanic | Detail | Source |
|---|---|---|
| SUMPRODUCT's native blank/text handling is NOT N/A-aware by default | SUMPRODUCT treats non-numeric array entries (blank cells, text) as zero, it does not exclude them; a blank or "N/A" score cell silently contributes 0 to the numerator while its full weight still contributes to a denominator built from `SUM(weights)`, dragging the average down rather than excluding the criterion. This is the specific defect an N/A-aware design must avoid. | [raw/datacamp-com-tutorial-sumproduct.md] |
| The double-unary inclusion-mask pattern | Build a boolean test for "this criterion applies" (e.g. `applicable_range<>"N/A"`), convert it from TRUE/FALSE to 1/0 with the double-unary operator `--`, and multiply that mask into the SUMPRODUCT alongside the value and weight arrays: `=SUMPRODUCT(--(applicable_range<>"N/A"), value_range, weight_range) / SUMPRODUCT(--(applicable_range<>"N/A"), weight_range)`. Rows where the mask evaluates to 0 contribute nothing to either the numerator or the denominator. | [raw/datacamp-com-tutorial-sumproduct.md] |
| The dual-masking requirement | Both the numerator and the denominator must apply the identical inclusion mask; if only the numerator excludes N/A rows while the denominator still sums the full (unmasked) weight range, an N/A criterion's weight still deflates the result even though its score no longer contributes to the numerator. This specific rollup-correctness pitfall is not spelled out verbatim by the SUMPRODUCT source itself (which documents the masking mechanism, not this particular failure mode); it is flagged here as a direct inference built from that source's own documented mechanism, not a directly quoted claim, and should be treated with that caveat. | [raw/datacamp-com-tutorial-sumproduct.md] |
| An independent, LLM-rubric-domain precedent for the same pattern | A rubric-grading framework (AutoRubric) implements essentially the same exclusion pattern under a different name: a criterion that cannot be assessed is marked `CANNOT_ASSESS` (`na=True`) and is excluded from the weighted sum entirely under its default "SKIP" strategy, rather than being scored as a failure or silently included as a zero. Its documented score formula is `weighted_sum = sum(verdict_value * criterion.weight for each criterion)` normalized by `total_positive_weight`, where "each criterion" already means "each retained, non-excluded criterion." This confirms the same drop-from-both-numerator-and-denominator principle from a second, independent source and domain (LLM evaluation rubrics rather than spreadsheet formulas), lending it more confidence as the right general pattern even though this second source is not itself about Excel. | [raw/autorubric-org-docs-api.md] |
| Guard against a zero-weight denominator | A related, generic SUMPRODUCT/weighted-average source (not itself about N/A-handling specifically, cited here only for the defensive-formula pattern) recommends wrapping the divide in an `IF` guard, e.g. `=IF(SUM(Weights)=0,"No weights",SUMPRODUCT(...)/SUM(Weights))`, to avoid a `#DIV/0!` error. This is directly relevant to N/A-aware rollups specifically because excluding enough criteria as N/A can legitimately drive the masked weight-sum to zero (e.g. every criterion in a sub-audit is N/A), a case the rollup engine must handle explicitly rather than let error out. | [raw/exceljet-net-formulas-weighted-average.md] |

Net assessment: the N/A-aware mechanism itself (mask-and-exclude from both numerator and denominator, guard the zero-denominator case) is now grounded in two independent sources from two different domains (spreadsheet formulas and LLM-rubric grading). The specific "why both sides must be masked identically" correctness argument is an inference from the SUMPRODUCT source's mechanism rather than a directly quoted statement, and is flagged as such rather than presented as sourced fact.

## 3. Generating branded, styled XLSX reports programmatically (Python/openpyxl)

| Mechanic | Detail | Source |
|---|---|---|
| Template injection is the recommended pattern for a branded deliverable | Rather than building a styled workbook from scratch in Python every run, load a pre-designed `.xlsx` template (logo, brand colors, formulas, print area already built by a human) with `openpyxl.load_workbook()`, write only into the specific data cells, and save as a new, dated output file, never overwriting the template. "The `.xlsx` is the source of truth for appearance; your script is responsible only for data." | [raw/python-excel-automation-com-generating-excel-reports-from-templates.md] |
| Why not `pandas.to_excel` for a branded template | `pandas.to_excel` targeting an existing sheet replaces the sheet contents wholesale, discarding the title banner, header fill, merged cells, totals formula, and print area; it is explicitly named "the wrong tool" for filling a branded template. Cell styles, column widths, conditional formatting, and named ranges survive an `openpyxl` write; images, charts, and data validation survive an `openpyxl` write but NOT a pandas rewrite of the same sheet. | [raw/python-excel-automation-com-generating-excel-reports-from-templates.md] |
| Never overwrite a formula cell with a value | `openpyxl` does not evaluate formulas, it stores the formula string verbatim and Excel computes the result on open; the rule is to write only to cells that hold data, never to cells that already hold a formula (e.g. a totals/rollup cell). If a computed value is needed back in Python, reopen with `load_workbook(path, data_only=True)`, but that only returns Excel's last-cached value and is `None` for a file never opened in Excel. | [raw/python-excel-automation-com-generating-excel-reports-from-templates.md] |
| Extending a template beyond its designed row range | If generated data exceeds the template's pre-built formula range (e.g. audit has more line items than the template was designed for), the formula itself must be extended in code (e.g. `ws["C13"] = "=SUM(C5:C12)"` after previously covering only C5:C9), or the range should be computed dynamically from the actual row count. Clearing unused template rows with `None` values is safer than `delete_rows`, which would also strip the template's formatting/conditional-formatting from those rows. | [raw/python-excel-automation-com-generating-excel-reports-from-templates.md] |
| Excel's own template file format | `.xltx` (and `.xltm` for macro-enabled templates) gives Excel-native no-overwrite behavior (double-clicking opens a copy), as an alternative/complement to the save-as-dated-filename script discipline above; `openpyxl` can `load_workbook()` an `.xltx` directly, output should still be saved as `.xlsx`. | [raw/python-excel-automation-com-generating-excel-reports-from-templates.md] |
| Conditional formatting API surface (official docs) | `openpyxl` exposes three families of conditional formatting: builtins (`ColorScale`, `IconSet`, `DataBar`, each with a convenience `*Rule` constructor), standard formats (Average, Percent, Unique/duplicate, Value, Rank), and custom formula-driven rules (`FormulaRule`) via differential styles (`DifferentialStyle` combining `Font`/`PatternFill`/`Border`). Rules are registered against an A1-style range string via `ws.conditional_formatting.add(range, rule)`. This is the exact API surface for visually flagging a final weighted score (e.g. a red/yellow/green `ColorScaleRule` on the final-score column) or flagging N/A-excluded rows (e.g. a `FormulaRule` testing for the N/A marker) in a generated report. | [raw/openpyxl-readthedocs-io-formatting.md] |

Named-range note: none of this round's three openpyxl/formula-mechanics sources specifically discuss embedding a company logo image (`ws.add_image`) or setting workbook-level named ranges as opposed to plain cell references as the branding/integrity mechanism; the template-injection pattern (Section 3) assumes the logo and branding already live in the human-designed template file being loaded, not that the Python script draws the logo itself. This narrows, but does not fully close, the round-2-flagged gap that "neither source specifically discusses Excel named ranges... as an integrity mechanism" (round-2 finding, still true of this round's new sources for named ranges specifically; exceljet's worked weighted-average example, cited in Section 1/2, does use a named range `weights`, which is the closest this archive comes to a named-range-driven design precedent). [raw/python-excel-automation-com-generating-excel-reports-from-templates.md] [raw/openpyxl-readthedocs-io-formatting.md] [raw/exceljet-net-formulas-weighted-average.md]

## 4. Multi-level rollup / rubric scoring engine design (leaf to sub-audit to category to final)

This was the second previously-unfilled gap: neither round-2 source described a multi-level rollup, only a single flat weighted sum across one row of criteria. One round-3 source partially closes it.

| Mechanic | Detail | Source |
|---|---|---|
| Positive/negative-weighted-sum-then-normalize pattern | `weighted_sum = sum(verdict_value * criterion.weight for each criterion)`, then `score = clamp(weighted_sum / total_positive_weight, 0, 1)`. Positive-weight criteria earn their weight when met and contribute 0 when unmet (a "reward" framing); negative-weight criteria instead SUBTRACT their weight when met and contribute 0 when unmet (a "penalty" framing), and negative weights are not normalized against their own weight total, only positive weights define the normalization denominator. This is a more elaborate rollup primitive than the flat single-sign SUMPRODUCT pattern in Section 1, and is directly relevant if this Bee's own scoring model needs a penalty/deduction class of criterion (e.g. a critical-security-style finding that subtracts from an otherwise-good score) alongside ordinary graduated criteria. | [raw/autorubric-org-docs-api.md] |
| What this source does NOT provide | The fetched AutoRubric API-reference page documents a single-level scoring model, one weighted sum over a flat set of criteria per rubric. It does not describe, on this fetched page, an explicit multi-level hierarchy (e.g. leaf criteria rolling into named sub-groups, which then roll into named categories, which then roll into one final score). The leaf-to-sub-audit-to-category-to-final structure this Bee implements is therefore still NOT directly grounded in any raw source in this archive; only the N/A-exclusion mechanic (Section 2) and the positive/negative-weight normalization mechanic (this row) are grounded, not the nesting/hierarchy itself. | [raw/autorubric-org-docs-api.md] |
| Practical implication | A multi-level rollup can likely be implemented by applying the Section 1/2 formula (masked, N/A-aware SUMPRODUCT-style weighted average) recursively, i.e. treat each sub-audit's rolled-up score as one more weighted "leaf" value feeding into its parent category's own weighted average, and so on up to a final score. This recursive-application approach is a reasonable architectural inference from the flat formula this archive does document, but it is an inference, not something any raw source states explicitly for a spreadsheet context. Flagged as unverified design reasoning rather than sourced fact. | (inference, not raw-sourced) |

## 5. Scoring scale design: numeric scale with written anchors

- legalclarity: "a 1-to-5 scale works well for most evaluations. Define what each number means before anyone starts scoring... Without written definitions, evaluators drift toward the middle of the scale and the scores lose their ability to differentiate vendors." [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md]
- portfoliohub: also a 1-to-5 scale, extending the anchor-writing requirement to every value, not just the endpoints: "Write the anchors for every score value, not just 5 and 1. The middle values are where scoring drifts." Validation test: "Two people scoring the same project independently and landing within one point is the test that your anchors work." [raw/portfoliohub-io-blog-project-prioritization-template.md]
- Both sources agree on the 1-5 scale and written per-value anchors as the mitigation for scorer drift toward the middle; a point of agreement, not disagreement, across two equivalent-tier sources. [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md] [raw/portfoliohub-io-blog-project-prioritization-template.md]

## 6. Pass/fail vs. graduated criteria: the closest analogue to a critical-security-override

- legalclarity draws an explicit two-category distinction for RFP requirements: "Mandatory items are pass/fail: if a vendor can't meet them, the proposal doesn't advance regardless of how strong the rest looks. Scored criteria use a graduated scale... Mixing these two types in the same column is a common mistake." Recommended structure: one column for the requirement, one for its type (mandatory or scored), one for the vendor's response. [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md]
- This pass/fail-overrides-the-graduated-score pattern gates a vendor out entirely before or independent of the weighted formula; it does not modify an already-computed FINAL weighted rollup, so it is only an analogue, not a direct match, to a critical-security-override mechanic. AutoRubric's negative-weight-as-penalty pattern (Section 4) is a closer mechanical match, since a negative-weight criterion directly subtracts from an already-accumulating weighted sum rather than gating pass/fail before scoring begins. [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md] [raw/autorubric-org-docs-api.md]
- portfoliohub does not use a mandatory/scored distinction at all; every criterion is graduated 1-5 and weighted, with no pass/fail gate. This reflects the two sources describing different evaluation domains (vendor RFP disqualification vs. portfolio project ranking), not a factual contradiction. [raw/portfoliohub-io-blog-project-prioritization-template.md]

## 7. Category weighting, criteria-count guidance, and spreadsheet-integrity controls

- legalclarity's rough weighting split for professional-services RFPs: roughly 40% technical capability, 25-30% pricing, 20% experience/references, 10-15% implementation approach; government RFPs weight price more heavily, technology purchases push more weight to technical criteria. [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md]
- portfoliohub caps criteria count deliberately: "Five criteria, maximum. Every extra criterion pulls the scores toward the middle until the ranking stops separating anything," with weights "agreed and locked before scoring starts." [raw/portfoliohub-io-blog-project-prioritization-template.md]
- Neither source's specific weight percentages are about a website audit's categories; both are illustrative of a different domain and should not be read as a recommended weight split for this plugin's own audit categories.
- legalclarity: lock the scoring tab so evaluation formulas are "invisible or read-only"; lock description/quantity columns in a pricing tab; use data-validation dropdowns to force standardized responses. [raw/legalclarity-org-how-to-build-an-rfp-excel-template-that-works.md]
- portfoliohub: one tab, no merged cells, one row per scored item; rank and cumulative-cost columns kept as formulas, "never typed, so nobody can nudge it"; the weight-check-sums-to-1 formula (Section 1) doubles as a visible integrity check; restrict conditional formatting to a single decision column, since "a sheet with color on every cell is unreadable on a projector." [raw/portfoliohub-io-blog-project-prioritization-template.md]
