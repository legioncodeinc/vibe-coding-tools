## 1. Security headers this Stinger should check for, by purpose

| Header | Purpose | Recommended value | Source |
|---|---|---|---|
| Content-Security-Policy (CSP) | Restricts which scripts/origins can load, mitigates XSS and data-injection attacks | Nonce-based (server-rendered HTML) or hash-based (static/cached HTML); example: `script-src 'nonce-{RANDOM}' 'strict-dynamic' https: 'unsafe-inline'; object-src 'none'; base-uri 'none';` | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] [raw/web-dev-articles-security-headers.md] |
| X-Frame-Options | Clickjacking prevention: controls whether the page can be framed | `X-Frame-Options: DENY`; OWASP notes CSP's `frame-ancestors` directive obsoletes this header for supporting browsers, and that it provides no protection on a redirect or a JSON API response since there is nothing to interact with | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] [raw/web-dev-articles-security-headers.md] |
| X-Content-Type-Options | Blocks MIME-sniffing, prevents non-executable content being reinterpreted as executable ("MIME Confusion Attacks") | `X-Content-Type-Options: nosniff` | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] [raw/web-dev-articles-security-headers.md] |
| Strict-Transport-Security (HSTS) | Forces HTTPS-only access even if a user attempts plain HTTP | `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`; OWASP warns a long max-age combined with a lapsed/revoked certificate can lock out legitimate users until the duration expires | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] [raw/web-dev-articles-security-headers.md] |
| Referrer-Policy | Controls how much referrer data leaks to other origins | `Referrer-Policy: strict-origin-when-cross-origin`; OWASP notes modern browsers already default to a similar restrictive behavior, but recommends setting it explicitly for older-browser users | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] |
| X-XSS-Protection | Legacy reflected-XSS filter in older IE/Chrome/Safari | OWASP: do not set it, or explicitly disable (`X-XSS-Protection: 0`); can itself introduce XSS in otherwise-safe sites; superseded by CSP | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] |
| Expect-CT | Certificate Transparency reporting | OWASP marks this deprecated (flagged with an explicit warning symbol in the source): do not use it, remove from existing code if present, since mainstream clients now require CT qualification independent of the header | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] |
| Content-Type | Prevents a resource being misinterpreted as HTML (XSS vector) | `Content-Type: text/html; charset=UTF-8`; must include `charset` specifically to prevent XSS in HTML pages | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] |
| Cache-Control | Prevents sensitive data persisting in caches | `no-store` for sensitive data (strict no-caching); `private` for user-specific, non-shared caching; note `no-cache` does NOT prevent caching, it only forces revalidation before reuse, a common misreading OWASP calls out directly | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] |
| Set-Cookie | Not itself a security header, but its attributes are security-critical | OWASP defers detail to its separate Session Management Cheat Sheet, not itself archived in this raw set | [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] |

## 2. Headers web.dev covers that OWASP's archived excerpt does not

The web.dev source organizes headers by threat model and names several that do not appear in the OWASP excerpt captured here: Trusted Types (enforces sanitization before data reaches dangerous JS APIs, recommended for sites handling sensitive user data alongside CSP); Cross-Origin Resource Policy (CORP, prevents a site's resources being included by a cross-origin page); Cross-Origin Opener Policy (COOP, protects a page's window from interaction by malicious cross-origin windows); Cross-Origin Resource Sharing (CORS, controls cross-origin access to resources, listed under "advanced capabilities"); and Cross-Origin Embedder Policy (COEP, paired with COOP to enable cross-origin isolation for powerful features like `SharedArrayBuffer`). [raw/web-dev-articles-security-headers.md] web.dev groups its recommendations into three tiers: headers recommended for all websites (X-Content-Type-Options, X-Frame-Options, CORP, COOP, HSTS), headers recommended specifically for sites handling sensitive user data (CSP, Trusted Types), and headers for sites with advanced capabilities (CORS, COEP). [raw/web-dev-articles-security-headers.md] Neither source conflicts with the other on the headers both cover (CSP, X-Frame-Options, X-Content-Type-Options, HSTS); web.dev is simply the broader of the two on cross-origin isolation headers, while OWASP is the broader of the two on legacy/deprecated headers (X-XSS-Protection, Expect-CT) and cache/content-type hygiene. Both are official docs (OWASP's own cheat sheet series; Google's web.dev), so where they do not overlap they should be read as complementary rather than one superseding the other.

## 3. CSP implementation detail: nonce vs hash strategy

web.dev gives the more concrete implementation guidance of the two sources: use a nonce-based strict CSP when HTML is server-rendered (generate a fresh nonce per request, set it as the `nonce` attribute on every script tag); use a hash-based strict CSP when HTML must be served statically or cached, e.g. a single-page application (scripts must be inlined, since most browsers do not support hashing external script files). [raw/web-dev-articles-security-headers.md] It names Google Photos as a real-world nonce-based strict CSP example, and CSP Evaluator as a tool for assessing a deployed policy (this tool reference itself is cut off mid-sentence in the archived text, so no further detail on it is available). [raw/web-dev-articles-security-headers.md] OWASP's CSP section is comparatively thin in the archived excerpt: it defines CSP's purpose and threat coverage (XSS, data injection, "data theft to site defacement to distribution of malware") but the archived text cuts off mid-sentence immediately after a "NOTE: This header is relev..." fragment, before any recommendation detail is captured. [raw/cheatsheetseries-owasp-org-cheatsheets-http-headers-cheat-sheet-html.md] For CSP specifically, web.dev is the more complete of the two sources as archived, not because it is more authoritative in principle (both are official docs) but purely because more of its text survived the fetch.

## 4. Client-side injection surface: what third-party tags actually inject

This is where the third-party-and-injection cluster sources become directly relevant to this Stinger's "client-side injection surface" scope item, read together with the header controls above. Google Tag Manager (GTM) is "the loader that injects every other marketing and tracking script" on a page, commonly the hub for Google Analytics plus ad-conversion pixels from Meta, LinkedIn, and TikTok. [raw/sme-mapree-dev-stack-tech-google-tag-manager.md] Its detection signatures are the `dataLayer` global, `window.google_tag_manager`/`google_tag_data`/`googletag` globals, the `googletagmanager.com/gtm.js` script URL, and its own generated HTML comment markers (`<!-- Google Tag Manager -->` / `<!-- End Google Tag Manager -->`). [raw/sme-mapree-dev-stack-tech-google-tag-manager.md] For a security posture audit, GTM's presence means the actual script-origin allowlist a CSP `script-src` directive would need to cover is not fixed at deploy time: a marketing-managed container can add new script origins without a code deploy or a CSP update, which is a structural tension with the nonce/hash-based strict-CSP approach both header sources recommend, since `strict-dynamic` (used in web.dev's own example CSP) is specifically the mechanism that lets a trusted, nonce-bearing script load further scripts without each one needing its own allowlisted origin. [raw/web-dev-articles-security-headers.md] [raw/sme-mapree-dev-stack-tech-google-tag-manager.md] Neither header source discusses GTM by name; this connection is inference from reading the two clusters together, not a stated cross-reference in either raw source.

## 5. Client-side injection surface: autonomous content/metadata modification tools

Search Atlas's OTTO Pixel is, by the vendor's own description, "a single script that connects your website to Search Atlas," after which OTTO "reads your pages, fixes what's holding your rankings back, and deploys the changes straight to your site, on its own, across any CMS," including meta tags, schema markup, and published content, by default without human approval unless "approval mode" is explicitly turned on. [raw/searchatlas-com-otto-pixel.md] This is a materially different risk shape from a passive tracking pixel: it is a single third-party script granted the ability to autonomously rewrite live page content and metadata. For a passive external security-posture audit, this is a client-side injection surface item worth flagging on its own terms, distinct from XSS/CSP concerns, because no header control discussed in sections 1-2 (CSP, X-Frame-Options, etc.) is described in either header source as mitigating a vendor's own authorized, intentionally-installed content-modification capability; CSP restricts what scripts CAN load and execute, not what an already-trusted, already-loaded script is authorized by the site owner to do. This connection is this Stinger's own inference from reading the two clusters together; the vendor page does not discuss CSP or security posture at all, and the header sources do not discuss OTTO or similar SEO-injection tools. Note again that the OTTO Pixel source is vendor marketing copy, not independent security analysis, so any claim about its actual default behavior in production should be reported to the user as vendor-self-reported.

## 6. Explicit gaps: TLS/certificate and payment-path integrity

Nothing in any of the four raw sources documents TLS/certificate configuration checks (cipher suites, certificate chain validation, expiry monitoring) beyond OWASP's one-line HSTS warning about a lapsed certificate combined with a long `max-age` value locking out users.
