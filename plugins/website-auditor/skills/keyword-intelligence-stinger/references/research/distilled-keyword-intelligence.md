# Distilled keyword-intelligence research

Dense reference distilled from `raw/`. Every claim below cites its source file in brackets. This plugin's binding keyword-source priority chain is: (1) Google Search Console MCP if connected and has data, (2) customer-supplied Google Trends export, (3) EXA/Firecrawl-style AI inference of keywords from crawled site content when no GSC/Trends data exists, (4) paid keyword API as last resort. This distillation covers all four tiers: tiers 1 and 2 from the round-2 archive (GSC export/API mechanics, Trends CSV export mechanics), and tiers 3 and 4 newly closed in this round-3 sweep (AI/statistical keyword extraction from crawled content, and paid keyword-API pricing/mechanics from DataForSEO and Ahrefs).

Research window: round 2 sweep 2026-08-18 (tiers 1 to 2); round 3 deeper sweep 2026-08-18 (tiers 3 to 4). Standards and vendor pricing pages are current as of fetch date.

## 1. Tier 1 mechanics: Google Search Console (API and MCP path)

| Mechanic | Detail | Source |
|---|---|---|
| UI export row cap | The Performance report's built-in CSV export caps at 1,000 rows per dimension; nothing in the UI signals that additional rows exist. Do not treat a UI/dashboard-style CSV export as complete. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Search Analytics API row limit | Up to 25,000 rows per request for query/page/country/device breakdowns, up to 50,000 rows for less granular reports. Paginate with `startRow` for larger pulls. This is the relevant limit for a Search Console MCP integration, since an MCP server built on this API inherits the same per-request cap. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Historical window | The Search Analytics API (and the standard GSC dashboard) exposes a 16-month rolling window. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Auth model | OAuth, not API keys: authenticate as a user or service account with verified ownership of the property. This applies per-property; N properties means N separate OAuth handshakes/sync setups if built by hand. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Quotas | 1,200 queries per minute (QPM) and 30,000 queries per day (QPD) per project; described as "generous" but real. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Anonymized queries | Excluded by default from API results but still counted in total impression figures, which is why API/export totals will not exactly match the GSC dashboard. The anonymized share is typically 30-50% of impressions and is described as "often the most informative" portion, i.e. the long tail. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Alternative: Bulk Data Export to BigQuery | Ships daily query/page/country/device/search-appearance data to a BigQuery dataset with no row limits and includes the `is_anonymized_query` flag (plus its associated impressions) rather than silently dropping that data. Setup: enable BigQuery API on a GCP project, in GSC go to Settings > Bulk data export, enter the project ID/dataset/region, grant `search-console-data-export@system.gserviceaccount.com` as a BigQuery Data Editor; tables begin landing within 48 hours. Forward-looking only, it does NOT backfill the 16 months of history GSC otherwise retains. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Practical pattern | "Most serious teams end up running bulk export for the forward stream + a one-time API backfill for the historical window," combined into a single queryable warehouse. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Example API call shape | `POST .../searchAnalytics/query` with `Authorization: Bearer $ACCESS_TOKEN`, JSON body carrying `startDate`, `endDate`, `dimensions` (e.g. `["query","page"]`), `rowLimit`, `startRow`. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |
| Example rollup query (Bulk Export/BigQuery) | Aggregate `searchdata_site_impression` by `query`, summing impressions/clicks, computing CTR via `SAFE_DIVIDE`, averaging position, filtering `is_anonymized_query = FALSE`, ordered by impressions descending. | [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] |

Implementation implication for Tier 1: when a Search Console MCP is connected, the concrete constraint to design around is the 25,000/50,000-row-per-request API ceiling (paginated via `startRow`) and the 16-month lookback, not the 1,000-row UI export cap (which does not apply to an API-backed MCP). "Has data" should be checked against a property with verified OAuth ownership; a property with no verified ownership or an empty 16-month window is the condition that should fall through to Tier 2. [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md]

## 2. Tier 2 mechanics: customer-supplied Google Trends export

| Mechanic | Detail | Source |
|---|---|---|
| Export path | Manual only, no account/sign-in required: run a search on trends.google.com, set filters (search type, geography, time range, category), then use the download icon on each of three separate modules (Interest Over Time, Interest By Region, Related Queries) to get a CSV immediately. | [raw/searchspy-io-google-trends-download-data.md] |
| Interest Over Time CSV contents | Date (week or month bucket) plus a relative interest score (0-100) per search term. Bucketing granularity depends on the selected time range: daily for under 90 days, weekly for 90 days to 5 years, monthly for 5+ years. | [raw/searchspy-io-google-trends-download-data.md] |
| Interest By Region CSV contents | Geographic unit (country, state, city, or metro) plus a relative interest score (0-100); higher indicates higher relative interest in that location, not absolute volume. | [raw/searchspy-io-google-trends-download-data.md] |
| Related Queries CSV contents | Query text plus either an interest score (Top queries) or a percentage growth figure (Rising queries); a query with extreme growth shows literally as "Breakout" instead of a percentage. | [raw/searchspy-io-google-trends-download-data.md] |
| Critical scale caveat | All exported data is relative (0-100), never an absolute search count. "You cannot determine actual monthly search volume from Google Trends CSV exports. A score of 87 tells you it's near peak, not how many people searched." A customer-supplied Trends export therefore can rank/shape keyword interest but cannot itself supply search-volume numbers. | [raw/searchspy-io-google-trends-download-data.md] |
| Multi-term normalization trap | When multiple terms are compared and exported together, their scores share one normalized 0-100 scale; exporting the same terms separately produces different numbers because each export gets its own maximum. A customer-supplied export must therefore be read as internally consistent only within the file it came from, not merged numerically across separate export files. | [raw/searchspy-io-google-trends-download-data.md] |
| File format | Standard UTF-8 CSV with a short metadata header row (search term, parameters used) before the data rows; e.g. in pandas, `pd.read_csv('multiTimeline.csv', skiprows=1)` to skip that header. | [raw/searchspy-io-google-trends-download-data.md] |
| No official API | There is no official Google Trends API. The unofficial `pytrends` Python library scrapes the site, is rate-limited, "frequently breaks when Google updates its UI," and is explicitly called out as "not suitable for production use," best for personal/ad-hoc research only. Paid third-party wrappers (e.g. one built on the Google Ads Keyword Planner API, or SerpAPI's Trends endpoint) are described as more reliable alternatives, at a per-query cost. | [raw/searchspy-io-google-trends-download-data.md] |

Implementation implication for Tier 2: the mechanics above assume a human-run manual export (three separate CSV downloads per query, no auth), consistent with "customer-supplied" rather than an automated pull. The auth model for this tier is therefore "none, it's a file the customer hands over" rather than an API credential; the binding constraint to enforce when ingesting a customer's Trends export is the relative-scale caveat (do not present Trends scores as search volume) and the cross-file normalization trap (do not merge scores from separately-downloaded CSVs as if on a shared scale). [raw/searchspy-io-google-trends-download-data.md]

## 3. Tier 3 mechanics: AI/statistical keyword inference from crawled content (no GSC/Trends data)

This tier applies when a site has no connected GSC data and no customer-supplied Trends export, so keywords must be inferred purely from what a crawl of the site's own pages contains.

| Mechanic | Detail | Source |
|---|---|---|
| A documented 4-tier local extraction cascade | One real crawler/classifier service (`crawl_core`) implements keyword extraction as an explicit fallback chain: JSON-LD structured data first, then spaCy noun-chunk extraction, then Open Graph tags, then YAKE (a statistical, unsupervised keyword-extraction algorithm) as the final fallback when nothing else yields terms. This is a concrete, working precedent for "infer keywords from crawled content" as a graduated cascade rather than a single method. | [raw/github-com-divyambhutani-crawl-core.md] |
| Two backend architectures for the same job | The same service offers a local backend (BART-MNLI zero-shot classification for page-type/topic, plus the 4-tier keyword cascade above; ~4GB image, ~3GB RAM, ~800ms on GPU / 5s+ on CPU, free) and a cloud backend (a single Gemini 2.5 Flash call that both classifies and extracts keywords inline; ~1.5GB image, ~512MB RAM, ~1-2s latency, ~$0.001/request). This is a direct, costed precedent for "local NLP pipeline vs. single LLM call" as the two implementation paths for Tier 3 keyword inference. | [raw/github-com-divyambhutani-crawl-core.md] |
| What the extraction actually returns | Real example output: keywords are short noun phrases pulled from page title/headings/body (e.g. "Cuisinart CPT-122", "2-Slice Compact Plastic Toaster", "Removable Crumb Tray"), alongside separate topic/category classification (IAB-style categories with relevance scores) and a one-line summary. Keywords and topics are distinct, parallel outputs of the same classification step, not the same list. | [raw/github-com-divyambhutani-crawl-core.md] |
| TF-IDF as an alternative/complementary statistical method | A separate production crawler product (Serpwise) extracts per-page keywords using TF-IDF (Term Frequency-Inverse Document Frequency) computed across the customer's own domain, explicitly weighting keywords "against your full page index" so the output highlights terms uniquely important to each page rather than common site-wide boilerplate terms. This is computed automatically as part of crawling, with no extra cost/credits and no separate configuration step. | [raw/serpwise-ai-docs-content-analysis.md] |
| TF-IDF's stated use case | Explicitly framed for verifying pages target their intended topics and for spotting content gaps, i.e. a diagnostic/audit use, not a search-volume or ranking signal. Consistent with Tier 3 being a fallback that describes what a site's content is about, not a source of real search demand. | [raw/serpwise-ai-docs-content-analysis.md] |
| Domain-relative weighting matters | TF-IDF's discriminative power specifically comes from weighting a page's terms against the rest of the same domain's pages, not scoring pages in isolation; an inference engine implementing Tier 3 for a single-page or very-small-site audit would have a weaker "distinctive keyword" signal than one with a fuller site crawl to weight against. | [raw/serpwise-ai-docs-content-analysis.md] |

Coverage note: neither of these two sources names EXA or Firecrawl by product name, and neither is an EXA/Firecrawl vendor doc. They are, however, real production examples of the same underlying methodology this plugin's Tier 3 describes (AI/statistical inference of keywords from crawled page content when no first-party search data exists): one via an LLM/NLP classification cascade, one via TF-IDF. Treat this as functionally-equivalent-methodology coverage, not brand-specific EXA/Firecrawl documentation, which remains unfetched.

## 4. Tier 4 mechanics: paid keyword API as last resort

| Mechanic | Detail | Source |
|---|---|---|
| DataForSEO Labs API scope | A single vendor API surfacing four billion-plus indexed keywords and 500 million-plus SERPs across Google's regional indexes, sub-2-second response times, combining Google Ads volume/CPC/competition data, DataForSEO's own proprietary keyword database, and clickstream-derived search volume/traffic estimates (positioned as independent of Google Ads' bucketed volume ranges). Endpoints relevant to this plugin: Keywords For Site (keywords relevant to a target domain), Keyword Suggestions (long-tail via full-text search), Related Keywords (up to 4,680 ideas per seed via Google/Amazon SERP "related searches"), Keyword Ideas (category-based, non-obvious terms), Search Intent (informational/navigational/commercial/transactional classification), Bulk Keyword Difficulty (0-100 score), Keyword Overview (CPC/competition/volume/intent/SERP/backlinks/clickstream in one call), Historical Keyword Data (back to August 2021). | [raw/dataforseo-com-apis-dataforseo-labs-api-keyword-research.md] |
| DataForSEO pricing model | Pay-as-you-go, no monthly commitment. Live Mode Search Intent: $0.0012/task + $0.00012/keyword = $121.20 per 1M keywords. Live Mode for other keyword-research endpoints: $0.012/task + $0.00012/item = $132 per 1M keywords/domains. A free trial and sandbox environment are available before paid usage; the vendor's own account-level rate limit for DataForSEO Labs API is 2,000 calls/minute, with higher quotas available on request. | [raw/dataforseo-com-apis-dataforseo-labs-api-keyword-research.md] |
| DataForSEO's stated resale posture | Pricing is explicitly "optimized for software builders" who resell the data inside their own tools to their own end users, per the vendor's own Terms-of-Service framing on this page, i.e. this plugin embedding DataForSEO data inside customer-facing audit reports is a supported, anticipated use case rather than an edge case requiring a special enterprise agreement. | [raw/dataforseo-com-apis-dataforseo-labs-api-keyword-research.md] |
| Ahrefs Keywords Explorer API shape | `GET /v3/keywords-explorer/matching-terms`, requires `country` and `select` (comma-separated output columns); optional `keywords`, `keyword_list_id`, `terms` (all vs. questions-only), `match_mode` (terms vs. exact phrase), `where` filter expression, `order_by`, `limit` (default 1,000, max 150,000). | [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md] |
| Ahrefs response fields | Per keyword: `volume` (avg monthly searches over latest known 12 months), `volume_monthly` (latest single month, cannot be used in `order_by`), `global_volume`, `cpc` (USD cents), `cps` (clicks-per-search ratio), `difficulty` (0-100 ranking-difficulty score), `intents` (boolean flags: informational/navigational/commercial/transactional/branded/local), `parent_topic`, `serp_features` (array of enriched-SERP element types present), `traffic_potential`, `first_seen`/`serp_last_update` timestamps, desktop/mobile volume split. | [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md] |
| Ahrefs billing model differs structurally from DataForSEO's | Several Ahrefs response fields are individually annotated "(10 units)" in the endpoint's own documentation (e.g. `volume`, `difficulty`, `intents`, `traffic_potential`, `global_volume`, `volume_monthly`), indicating Ahrefs bills per requested field on a unit basis rather than DataForSEO's flat per-task-plus-per-item structure. A cost-conscious Tier-4 integration should request only the specific fields actually needed (e.g. `volume` and `difficulty` alone) rather than the full field set, since each additional field appears to add its own unit cost. This is an inference drawn from the per-field unit annotations in the source, not an explicit pricing statement in the fetched page (no dollar-per-unit conversion rate was present in what was fetched). | [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md] |
| Ahrefs also exposes an MCP surface | The endpoint is explicitly labeled "API + MCP" in its own documentation, meaning Ahrefs itself ships an MCP-compatible interface to this same keyword data, a second, brand-named MCP path distinct from this plugin's own Tier-1 Search-Console-MCP concept but architecturally analogous to it. | [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md] |
| Cost comparison across the two vendors | For a straightforward "get search volume for N keywords" call, DataForSEO's flat ~$132 per 1M keywords/domains is directly comparable in shape to a rough per-keyword cost; Ahrefs' unit-based-per-field billing does not reduce to a single comparable per-keyword figure from what was fetched, since the price-per-unit was not stated on the fetched page. A cost comparison between the two vendors is therefore only partially possible from this archive: DataForSEO's cost is a firm, quoted number; Ahrefs' cost requires knowing its price-per-unit, which was not present in the fetched documentation. Flagged as a gap rather than estimated. | [raw/dataforseo-com-apis-dataforseo-labs-api-keyword-research.md] [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md] |

Implementation implication for Tier 4: both vendors require a paid account and per-call cost tracking, consistent with "last resort" framing, i.e. this tier should be gated behind an explicit cost/budget check rather than called opportunistically the way Tier 1-3 can be. DataForSEO's own resale-friendly pricing/ToS framing and firmer flat-rate pricing make it the more directly costable of the two vendors from this archive alone; Ahrefs' data is richer per keyword (search intent breakdown, SERP features, parent topic, traffic potential) but its true per-keyword cost cannot be computed from what was fetched. [raw/dataforseo-com-apis-dataforseo-labs-api-keyword-research.md] [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md]

## 5. Where sources agree, disagree, or don't overlap

- Tiers 1 and 2 address different Google products (GSC vs. Trends) and never make competing claims about the same fact. [raw/getdadseo-com-blog-export-google-search-console-data-csv-api.md] [raw/searchspy-io-google-trends-download-data.md]
- Tier 3's two sources (crawl_core, Serpwise) describe genuinely different mechanisms, LLM/NLP classification cascade vs. TF-IDF, for the same underlying job (infer distinctive keywords from crawled page content), and are complementary rather than conflicting: crawl_core's local-backend cascade explicitly falls back to a statistical method (YAKE) when its earlier NLP tiers find nothing, and Serpwise's TF-IDF is itself a similar statistical fallback used as a primary rather than last-resort method. Neither source is more authoritative than the other on which approach a Tier-3 implementation should default to; both are same-tier sources (a community GitHub project and a vendor product doc, respectively), and the choice is an architectural tradeoff (local NLP dependency weight and latency vs. simpler statistical computation) rather than a factual disagreement. [raw/github-com-divyambhutani-crawl-core.md] [raw/serpwise-ai-docs-content-analysis.md]
- Tier 4's two sources describe two different vendors and pricing models that are not directly comparable on a like-for-like dollar basis from what was fetched (see the cost-comparison row in Section 4); this is a genuine information gap, not a factual contradiction between the sources. [raw/dataforseo-com-apis-dataforseo-labs-api-keyword-research.md] [raw/docs-ahrefs-com-api-reference-keywords-explorer-get-matching-terms.md]

## 6. Remaining coverage gaps in this archive

- Tier 3 is grounded in functionally-equivalent methodology (a real 4-tier NLP/statistical extraction cascade, and a real TF-IDF-based extraction pipeline), but neither raw source is an EXA or Firecrawl product document by name. If this plugin's Tier 3 is meant to invoke EXA's or Firecrawl's own specific API/product mechanics (endpoint shapes, pricing, rate limits) rather than the general inference methodology, that brand-specific documentation is still not archived and should be flagged as a gap in any implementation that needs EXA/Firecrawl-specific API details.
- Tier 4's Ahrefs pricing could not be reduced to a firm per-keyword dollar figure from the fetched documentation (see Section 4); only DataForSEO's pricing is fully quoted. A cost-based vendor recommendation between the two should not claim Ahrefs is cheaper or more expensive than DataForSEO without pulling Ahrefs' own pricing page.
- No source in this archive (round 2 or round 3) discusses how this plugin should decide, in code, whether Tier 1's "has data" check has failed cleanly enough to fall through to Tier 2, or how Tier 2's manual customer-export ingestion should be validated before falling through to Tier 3; the tier-transition logic itself remains an implementation decision not directly grounded in any raw source here.
- Round-3 archive size: 4 new sources (crawl_core, Serpwise docs, DataForSEO Labs pricing page, Ahrefs Keywords Explorer API docs) added to the 2 round-2 sources (getdadseo.com, searchspy.io), for 6 raw sources total. Treat any inference beyond what is directly quoted or tabled above as unsupported by this archive.
