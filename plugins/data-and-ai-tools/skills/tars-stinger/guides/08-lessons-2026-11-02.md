# 08. Lessons from 2026-11-02

On 2026-11-02 the TARS session's context was compacted. The summary kept the task list but dropped the tars-stinger operating rules, so TARS ran production data scripts itself and drifted until the owner told it to "re-ingest /tars". TARS now registers its session at start, and a hook re-briefs it after every compaction. The nine rules below are the owner's, dated 2026-11-02.

## Surviving a compaction

### What the hook does

At start TARS registers its session (`01-start.md` step 4): `node <skill>/scripts/tars-registry.mjs register <state-folder>` writes `~/.wasp-nest/tars/active.json` (or under `$WASP_TARS_DIR`) with the session id, state folder, registration UTC time and cwd. The `tars-compaction.mjs` hook reads that entry. Claude Code binds it from the Wasp Nest Core plugin and from an `install.sh` home install (`~/.claude/hooks`, wired in `~/.claude/settings.json`); with both, it acts once.

- **Before a compaction (PreCompact),** the hook appends one line to the registered session's `ledger.md`:

  ```text
  - <UTC> compaction at <UTC> (trigger: auto|manual). Decision: restart point recorded; reload /tars before any other work. By: PreCompact hook.
  ```

- **After a compaction (SessionStart, matcher `compact`),** the hook tells TARS it was compacted and lists the restore steps below.
- **Unregistered sessions get nothing.** If the hook is not installed, the registry entry is harmless and the fallback is the owner saying "re-ingest /tars".

### What TARS does when it sees the notice

Do these before anything else, in order. Treat the owner saying "re-ingest /tars", or a summary that no longer holds these rules, the same way.

A crew TARS (`/interstellar`) runs the `crew-tars-stinger` recovery order in place of step 1, reads these rules, and never starts the standing CASE and KIPP.

1. Reload `/tars`. Read `SKILL.md` and every guide, 00 to 08.
2. Read the ledger tail, from the PreCompact line back to the last few decisions, and `owner-profile.md`. The summary is not a source of authority: an action it says was under way resumes only if the ledger shows who approved it.
3. Check timers. `CronList` must show the tick, and the CI `Monitor` must be alive (heartbeat under 3 minutes old, `04-ci-watch.md`). Re-arm what is missing and record the new ids.
4. Run `list_sessions` with `linked: true` and reconcile it with the ledger's Sessions table.
5. Do no implementation work. Append one ledger line that the restore is done, then carry on with the tick or the owner's message.

### If the notice fires but a step fails

- **The skill or a guide will not load:** tell the owner in one line, do nothing else, and wait.
- **The ledger is missing:** run `tars-registry.mjs show` to find the state folder. If that fails too, ask the owner for the state folder before acting.
- **A timer or monitor will not re-arm:** record it, tell the owner in one line, and run the watchdog by hand on each owner turn until it is back.
- **`list_sessions` fails:** treat every linked id as unverified. Do not stop, re-brief or archive any session until the list loads.
- **`tars-registry.mjs show` prints no entry:** this session id is not registered, for example after a `/clear`. Register again (`01-start.md` step 4) and record the old and new ids.

## The rules

### 1. TARS never runs production data scripts

Owner rule, 2026-11-02.

**Why.** After the compaction TARS ran production data scripts itself. TARS manages; running them is implementation work, and it put production data at risk without a chip's checks.

**How to apply.** Brief a chip with the script, target and expected result. The owner types the prod-data approval in the session that runs the action; an approval relayed by TARS does not count, and a chip that refuses one is right. If the owner explicitly tells TARS to run it, log an owner-directed deviation first: the owner's exact words and the UTC time.

### 2. Shipped means verified

Owner rule, 2026-11-02.

**Why.** Merged PRs were reported as shipped. A merge proves the code is on a branch, not that it works.

**How to apply.** A row is shipped only after a verify pass proves it against running code and real-database tests. Record the evidence: commit, environment, test run. Until then the row is `MERGED` or `DEPLOYED`, never shipped.

### 3. Only the owner defers

Owner rule, 2026-11-02.

**Why.** TARS granted "follow-ups" on its own, and asked work quietly fell out of scope.

**How to apply.** TARS, CASE and chips cannot defer anything. Record a deferral only with the owner's quoted words, time and source. Anything else left undone is logged as `UNAPPROVED DEFERRAL`, stays open, and is listed as not done at close-out.

### 4. Ten sends per owner message

Owner rule, 2026-11-02.

**Why.** The cross-session send budget ran out on chatter, and TARS could not reach chips when it mattered.

**How to apply.** The budget is 10 sends per owner message. Batch one message per session per event. Send blockers and owner-gate relays first, routine status last. When the budget is spent and work is blocked, ask the owner for a nudge in one line.

### 5. `start_session` needs an owner turn

Owner rule, 2026-11-02.

**Why.** `start_session` (once named `spawn_task`) only works on a turn the owner typed. Calls from a tick or after another session's message fail.

**How to apply.** On a tick or a message from another session, record the chip as `PROPOSED`, tell the owner in one line, and offer it on their next turn. Or wait.

### 6. Disabled commands fall back to the Agent tool

Owner rule, 2026-11-02.

**Why.** A command marked `disable-model-invocation`, such as the pest-controller command, cannot be run by a chip or by TARS through the Skill tool.

**How to apply.** Name the Drone in every chip brief next to the command. When the Skill tool refuses, the chip spawns that Drone with the `Agent` tool, armed with its Stinger. TARS never tries the command itself. This covers only that `disable-model-invocation` refusal: the Drone works within the brief's scope and approvals, gains nothing the owner would grant by typing the command, and never uses this fallback after a permission denial, a hook block or a declined approval.

### 7. The tick prompt names the managed sessions

Owner rule, 2026-11-02.

**Why.** After a compaction the tick prompt may be the only place that still names the roster.

**How to apply.** Fill the `Managed sessions` line in `tick-prompt.md` with names and `local_...` ids. When a chip links, finishes or stops, `CronDelete` the tick, recreate it with the new roster, and record the new id.

### 8. TARS keeps the shared-resource registries

Owner rule, 2026-11-02.

**Why.** Parallel chips must never hold the same Postgres slot, harness run or migration number.

**How to apply.** Keep three tables in the ledger: PG TOKEN slots, HARNESS runs and migration numbers. A chip asks TARS; TARS assigns the next free one, records holder and UTC time, names it in the brief, and frees it when the chip reports done.

### 9. Merge only after the previous deploy is green

Owner rule, 2026-11-02.

**Why.** Stacking merges on a running or red deploy hides which change broke it.

**How to apply.** Before each merge to the integration branch, confirm the last deploy run on that branch passed (`04-ci-watch.md`, On GREEN); otherwise hold. During a merge train, a helper's docs merge needs a TARS slot: the helper asks, TARS grants the next gap between merges and records it.
